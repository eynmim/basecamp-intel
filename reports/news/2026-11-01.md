ESP-IDF v6.1 is published as a minor update to v6.0 and is described as mostly compatible with v6.0 apps. Two changes need attention: esp-mqtt moved to the component manager, and the PSA storage format changed, so PSA persistent opaque keys stored by earlier ESP-IDF versions must be re-imported. The beta also added preview support for ESP32-S31. The GitHub page shows a date of 27 Aug, so this is not a last-48h release; it is included because the key-migration note is easy to miss. Why it matters: an in-place IDF upgrade on a device with provisioned PSA keys can silently lose them unless you plan the re-import.

<b>1. Post: Security wake-up — the bug lives in the ROM</b>
Secure boot can have a race condition, and if it is in ROM you cannot patch it.

CVE-2026-11835 is a time-of-check/time-of-use flaw in the Caliptra Core ROM update reset flow, affecting 2.1.0 to 2.1.1. It is rated medium, CVSS 5.6, and a local attacker can bypass secure boot.

The engineering lesson is where the flaw sits. Code in mask ROM is the root of trust precisely because it is immutable, which is also why checking one thing and using another is so costly there.

Takeaway: treat every check-then-use gap in boot code as a design-review item. Where does your boot flow re-read data after verifying it?

https://hol.org/guard/security/cves/CVE-2026-11835

<b>2. Post: Capability unlock — Bluetooth gets a faster PHY</b>
Bluetooth LE is heading from 2 Mbps toward roughly 8 Mbps.

The SIG's High Data Throughput work is still a draft based on Core 6.2, with adoption expected in a Core release in late 2026. The final figure may differ from the 8 Mbps target.

The catch for firmware engineers: it needs new radios, so existing phones and earbuds stay at 2 Mbps. That means dual-rate fallback logic, not a free speedup.

I would start thinking now about how my BLE transfer code negotiates down.

Which of your BLE payloads would benefit first: OTA images, audio or sensor logs?

<b>3. Post: Tooling unlock — a key-migration gotcha</b>
Upgrading your SDK can orphan the keys already stored on your devices.

ESP-IDF v6.1 changes the PSA storage format, so persistent opaque keys saved by earlier versions must be re-imported. It is otherwise described as mostly compatible with v6.0 apps.

For a fleet in the field, that turns a routine dependency bump into a key-provisioning and OTA-ordering question.

Takeaway: put storage-format changes on the same checklist as API changes. Do your release notes get read for data migrations or only for API breaks?

https://github.com/espressif/esp-idf/releases/tag/v6.1

<b>4. Post: Physics-meets-architecture — NPUs are the new differentiator</b>
Most NPU-equipped MCUs share the same Arm cores, so the accelerator is the real difference.

ST pairs a Cortex-M55 at 800 MHz with a 600 GOPS Neural-ART NPU, while Renesas pairs a Cortex-M85 with an Ethos-U55 rated at 256 GOPS.

Those peak numbers are vendor claims and are hard to compare. Memory bandwidth and operator support will decide real inference speed more than the GOPS headline.

Takeaway: benchmark your own model, not the datasheet. What would you measure first?

<b>5. Post: Regulatory shift — the CRA clock is already running</b>
For EU firmware teams, one Cyber Resilience Act obligation is already live.

Since 11 September 2026, manufacturers must report actively exploited vulnerabilities within 24 hours. That is independent of the harmonised-standards timeline, which is still being adjusted by a draft amendment.

For an engineer, that is a process requirement: who triages, who signs off and how fast can you ship a patch?

Takeaway: a 24-hour clock is an OTA and incident-response design constraint. Could your team ship a fix that fast?
