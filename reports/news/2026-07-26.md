Espressif shipped ESP-IDF v5.5.5 in mid-July as a bugfix release that disables the ECDSA-based Secure Boot V2 verification flow on three chips — ESP32-H2, ESP32-C5, and ESP32-P4 — after a vulnerability was found in that specific code path, meaning any device on those targets shipping with ECDSA secure boot enabled needs to reassess its boot-chain trust model right now, not at the next audit cycle. Why it matters: ESP32-S3 shares the ESP-IDF codebase and crypto/Secure Boot infrastructure with H2/C5/P4 — this isn't an S3-specific vulnerability, but it's a concrete reminder to read ESP-IDF security advisories per-target rather than treat "Secure Boot enabled" as a static guarantee.

<b>1. Post: Security wake-up — the boot check that got turned off</b>
Espressif just shipped a firmware update whose main job is disabling a security feature.

ESP-IDF v5.5.5 turns off the ECDSA-based Secure Boot V2 verification flow on three chips — ESP32-H2, ESP32-C5, and ESP32-P4 — after a vulnerability was found in that exact code path. Anyone shipping those targets with ECDSA secure boot enabled now has a boot chain that trusts less than it did last week.

The part worth sitting with: "Secure Boot enabled" in your build config isn't a permanent guarantee, it's a snapshot of one code path's correctness at build time. This release is a reminder to actually read per-target security advisories instead of treating a checkbox as a fact.

If you've got Secure Boot on in production, when did you last check whether it still means what you think it means?

<b>2. Post: Capability unlock — always-on AI that outlives the coin cell's shelf life</b>
Under 100 microwatts. That's what it now costs to keep an AI model listening for a wake word, all the time, forever.

Ambient Scientific's GPX10 Pro packs ten programmable AI cores rated at 512 GOPS peak next to an Arm Cortex-M4F host, and its always-on keyword-spotting mode draws under 100µW — low enough to run for years on a single coin cell without ever sleeping the AI path.

The interesting shift isn't the GOPS number, it's the power budget: always-on inference used to mean either duty-cycling the model or accepting a battery that dies in months. This is the first time I've seen a coin-cell-class part make "always listening" a genuinely free assumption in the power budget.

<b>3. Post: Tooling unlock — ONNX finally speaks RISC-V fluently</b>
Running an ONNX model on a RISC-V MCU used to mean a lot of hand-rolled kernels. That gap just got smaller.

ONNX Runtime v1.28.0 adds RISC-V Vector (RVV) support directly to the CPU execution provider, alongside a standalone WebGPU Plugin EP and better NPU discovery via sysfs for containerized edge deployments — plus 30+ security fixes across kernels and model loaders.

The RVV addition matters more than a changelog line suggests: it's one less reason to reach for a hand-optimized inference stack the moment a project moves off Arm Cortex-M onto something like an ESP32-P4. Mainstream ML tooling catching up to RISC-V silicon, instead of RISC-V waiting on tooling, is the direction that needed to happen.

<b>4. Post: Physics-meets-architecture — a GPU that fits inside an MCU's power budget</b>
A display GPU used to mean a separate chip. STM32H7R7 puts one inside the MCU package instead.

The new ART-Pi II board runs a 600MHz Cortex-M7 STM32H7R7 with an optional NeoChrom 2.5D GPU built into the same silicon, handling blitting, blending, and scaling for embedded GUIs — plus 32MB HyperRAM and 64MB HyperFlash on a $45 board with a Pi-compatible header.

The architecture insight: once a fixed-function block is cheap enough to fit inside an MCU's die and power envelope, the "add a graphics coprocessor" BOM line disappears entirely. It's the same trend reshaping edge-AI silicon with NPUs — dedicated accelerators moving from add-on chip to on-die feature as soon as area and power allow it.
