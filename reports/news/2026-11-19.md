<b>═ 🔥 TOP STORY ═</b>
Zephyr published CVE-2026-95823 (High, CVSS 7.5) on 18 Nov. It is a use-after-free and buffer leak in tcp_pkt_linearize() that has been in the TCP stack since a June 2020 commit. When a TCP header spans two net_buf fragments, the code unrefs the emptied fragment while it is still linked to the chain, which frees the payload buffers after it too. It also drops a fragment that still holds data without releasing it. tcp_recv() reaches this before connection lookup or header validation, so one unauthenticated segment to any listening socket is enough. An off-link attacker can push the header across a buffer boundary with an IPv6 Destination Options header of a chosen length, and 6LoWPAN or IP reassembly can do the same. The reliable effect is one leaked RX buffer per crafted segment until the pool runs dry and the device goes deaf until reboot. Every release from 2.3.0 up to 4.3.2 and 4.5.0 is affected, and there is still no fixed 4.4.x or 3.7.x LTS tag, only merged branch backports. Why it matters: any networked Zephyr product with a listening TCP socket and no default-off config to hide behind needs 4.3.2, 4.5.0 or a branch build.

<b>1. Post: Security wake-up — one TCP segment, six years of exposure</b>
A Zephyr TCP bug that shipped in 2020 was disclosed yesterday, and reaching it needs no handshake.

CVE-2026-95823 is in tcp_pkt_linearize(), which copies a TCP header together when it spans two network buffers. tcp_recv() calls it before connection lookup and before header validation, so one unauthenticated segment to any listening port is enough.

The insight is in how an attacker gets the header to straddle two buffers: an IPv6 Destination Options header of a chosen length. The receive path accepts it and shifts the TCP header wherever the attacker wants. Then the code frees a fragment that is still linked to the rest of the chain, and the payload goes with it.

The reliable result is a leaked RX buffer per packet until the device stops receiving entirely.

Does your watchdog notice a device that is running but deaf?

<b>2. Post: Tooling unlock — Arduino-ESP32 4.0 goes stable</b>
Arduino-ESP32 4.0.0 shipped today, and the version number matters more than the changelog.

On Arduino, the core version decides which ESP-IDF you build on, and so which IDF fixes and features you get. The 4.0 line has been built on ESP-IDF v6.1 since RC1. Two days ago 3.3.13 moved the 3.x line to IDF 5.5.6+, so both lines are now current.

The release also adds ESP32-S31 support, IPv6 DNS configuration, setCiphers() for TLS clients, UAC1/UAC2 USB audio at multiple sample rates, and lambdas for timers.

Small changes can break things: WiFi.SSID() now returns the saved SSID even when disconnected. If your code treated a non-empty SSID as "connected", it now has a bug.

Moving now, or waiting for 4.0.1?

<b>3. Post: Integration leap — the robot joint MCU</b>
GigaDevice now sells a Cortex-M7 aimed at a single robot joint.

The new-generation GD32H7 portfolio, announced 10 Nov, includes the GD32H77R for robotic joint servo control. GigaDevice's own material pairs it with an EtherCAT subdevice controller and multiple encoder interfaces, and the family runs at up to 750 MHz.

Here is what changes for engineers. Field-oriented current control, encoder decoding and the EtherCAT slave have often meant an MCU plus a separate EtherCAT slave controller on every joint board. Bringing the fieldbus onto the control MCU cuts BOM and board area per axis, and on a humanoid with 20+ joints that multiplies.

Samples are reported for January 2027.

Would you trust a single MCU with both the current loop and the fieldbus timing?

<b>4. Post: Regulatory shift — published is not the same as presumed</b>
The first CRA cybersecurity standards may be out in days, and on their own they will not give CE-mark comfort.

EN 40000-1-1 and -1-2 were reportedly ratified on 2 Nov. Trackers give 18 or 25 Nov for publication, and I have not seen a CEN-CENELEC notice confirming either.

The engineering point: under the CRA, a harmonised standard gives presumption of conformity only once it is cited in the Official Journal. Reports say CEN does not expect either part to be cited. The part expected to be cited is prEN 40000-1-3, on vulnerability handling.

So the first CRA standard with legal effect is likely to be about process: how you take in upstream CVEs, triage them and ship fixes. Zephyr alone published ten advisories in the past week.
