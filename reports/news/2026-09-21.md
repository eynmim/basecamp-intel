<b>1. Post: Security wake-up — one API call, unauthenticated, root on the identity platform</b>
CVSS 10.0 isn't rare because bugs aren't severe. It's rare because "unauthenticated" and "root" don't usually appear in the same sentence.

Cisco disclosed CVE-2026-76460 this week: a missing auth check on a single management-plane API endpoint in Identity Services Engine. Send one crafted request, get root command execution — no credentials, no workaround beyond restricting network reachability to the management interface.

The part I keep coming back to: ISE is a hardened appliance built specifically to manage network access policy. If insufficient auth control on an admin API can happen there, it can happen on the config or OTA endpoint you just wired into your own device's web UI over a long weekend.

Does your device's admin interface actually verify who's asking, or just where they're asking from?

<b>2. Post: Regulatory shift — the EU just started a 24-hour clock on your firmware bugs</b>
For the first time, the Cyber Resilience Act has actual teeth, and they landed ten days ago.

Since September 11, 2026, manufacturers selling connected products into the EU must report actively-exploited vulnerabilities to ENISA within 24 hours of becoming aware, via a new Single Reporting Platform, with a 72-hour follow-up and a 14-day final report. Fines run up to €15M or 2.5% of global turnover. This is a full year ahead of the rest of the CRA's product-security regime.

The practical shift: "we'll patch it when we get to it" stops being a viable internal policy the moment your product ships with a CE mark. You need a vulnerability-intake process and a named owner before you need the 24-hour clock, not after.

If you shipped a connected product into the EU, could you actually hit that 24-hour window today?

<b>4. Post: Physics-meets-architecture — the BLE bug that isn't a memory-corruption bug</b>
No buffer overflow, no stack smash. Just a state machine that trusted the wrong thing.

CVE-2025-62235 in Apache NimBLE lives entirely in the pairing logic: a crafted SMP Security Request packet gets accepted even when a legitimate bond already exists, letting an attacker strip that bond and re-pair as the impostor device — with a CVSS of 8.1 and zero user interaction required. It's fixed in NimBLE 1.9.0.

What makes it interesting architecturally is that BLE pairing security ultimately reduces to a protocol state machine, and state machines are only as trustworthy as their transition guards. "Is there already a bond?" is a one-line check that got missed, and the consequence was a full authentication bypass.

Next time you review a pairing or handshake flow, are you auditing the transition guards as carefully as the crypto?
