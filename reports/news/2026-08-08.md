<b>═ 🔥 TOP STORY ═</b>
The Zephyr Project shipped v4.4.2 on August 7, closing 68 CVEs in a single maintenance release — NULL-pointer dereferences and memory corruption in the Bluetooth BAP/HFP/SDP stack, a WireGuard receive-path heap overflow, a DNS resolver out-of-bounds read, USB CDC-NCM deadlocks, and race conditions in kernel thread allocation, among roughly 150 fixed issues total. The project has also confirmed more embargoed CVEs are queued for disclosure through August 26, meaning this isn't the end of the patch cycle. Zephyr is one of the few general-purpose RTOSes with a real published CVE program, so a 68-in-one-release count is less an indictment of the project and more a sign the disclosure pipeline is actually working — the alternative is silent bugs in codebases with no CVE program at all. Why it matters: if any coursework, thesis, or side project boots Zephyr instead of FreeRTOS, treat v4.4.1 and earlier as unsupported for anything network- or Bluetooth-facing until you've pulled 4.4.2.

<b>1. Post: Security wake-up — 68 CVEs, one release, and that's the healthy outcome</b>
Zephyr just patched 68 CVEs in a single release. That's not the scary number here — the scary number is how few other RTOSes could show you a list that specific.

Zephyr 4.4.2, shipped August 7, closes vulnerabilities across Bluetooth (BAP, HFP, SDP), networking (DNS resolver, WireGuard), USB, and kernel thread handling. More embargoed CVEs are queued for disclosure through August 26.

The instinct is to read a big CVE count as "this RTOS is buggy." Flip it: Zephyr has a real CVE program with assigned IDs, severity ratings, and a public disclosure calendar. Most embedded codebases running in the field right now have equivalent bugs with no CVE number attached, because nobody's counting.

If you're evaluating an RTOS for a safety- or security-relevant project, would you trust the one with a visible CVE backlog more, or less, than one with none?

<b>3. Post: Regulatory shift — the CRA deadline everyone assumes moved, didn't</b>
A lot of teams think the EU's August 30 cybersecurity deadline just got pushed back two months. It didn't.

What actually moved is the drafting timeline for the harmonised technical standards manufacturers are supposed to build against — delayed by a Commission amendment circulating since early July. The compliance obligation itself, written into Regulation (EU) 2024/2847, still lands August 30, 2026, exactly as originally set.

That gap between "the standard is late" and "the deadline moved" is where compliance mistakes happen — teams that deprioritize CRA work assuming an extension that was never actually granted to them.

If your team is tracking a CRA deadline, is it pinned to the regulation's text or to what people are saying in Slack?

<b>4. Post: Physics-meets-architecture — one PMIC, two independent power inputs, no coordination logic</b>
Harvesting energy from two different sources at once used to mean two separate power paths fighting for the same battery terminal. e-peas built a PMIC that just handles both.

The AEM15820 manages hybrid indoor and outdoor photovoltaic harvesting — microwatts to watts — on a single chip, with a cold-start circuit that comes alive from as little as 275mV input. Previously, covering that range meant stacking multiple PMICs and building arbitration logic between them.

The design insight worth sitting with: cold-start voltage is the real constraint in energy harvesting, not average power. A chip that wakes up at 275mV survives dawn, dusk, and indoor LED conditions that would leave a higher-threshold PMIC stuck off.

Anyone designing battery-free sensor nodes — is dual-source harvesting on one chip enough to change your PV cell selection?

<b>5. Post: Capability unlock — an open NPU instruction set that runs an LLM on a dev board</b>
An open-source NPU built on RISC-V is now running a real language model, fully on-device, on a board you can buy.

The Coralboard from Google and Synaptics pairs a 1 TOPS Coral NPU — RISC-V-based, with TensorFlow Lite and MLIR compiler support baked in — with Gemma 3's 270M-parameter model running entirely locally. The NPU IP itself is open-sourced for anyone to license.

What makes this different from another "edge AI dev board" announcement is the instruction set choice: an open NPU architecture means the compiler toolchain and model-deployment path aren't locked to one vendor's silicon roadmap, the same bet RISC-V made for CPUs years ago.

If NPU IP goes the way CPU IP did with RISC-V, does that change which silicon you'd bet on for a TinyML project three years out?
