<b>1. Post: Security wake-up — your WireGuard key isn't as safe as you think</b>
A stale API session is all it takes to pull a "military-grade" VPN key out in plaintext.

CISA disclosed CVE-2026-14227 this week: on MikroTik RouterOS, an API session can retain its old, more-privileged permission set after an inactivity timeout or a user-group change. With only low-privilege API access, an attacker can ride that stale session to extract the router's WireGuard private key — in plaintext — enabling full VPN impersonation and decryption of everything that key ever protected.

The interesting part isn't WireGuard, which is fine. It's that the vulnerability lives entirely in how long a permission grant is allowed to outlive the check that created it — a bug class that shows up just as easily in a custom ESP32 web config portal as in a router's management API.

If your firmware has an API or config server, when was the last time you checked whether a session can still act on permissions it no longer has?

<b>2. Post: Capability unlock — the fastest way to speed up inference is to stop computing it in software</b>
76% faster. 23% less power. Same silicon, same model — one config flag.

MLPerf Tiny v1.4 results are out, and STMicroelectronics' own submission shows what happens when you enable the STM32U3's hardware signal processor for image classification: inference time drops 76.0% and power draw drops 23.3%, compared to running the identical workload on the plain Cortex-M33 core.

That's not a smaller model or a better compiler — it's the same math executed by dedicated silicon instead of general-purpose instructions. It's a reminder that on MCU-class edge AI, the biggest wins increasingly come from matching the workload to purpose-built hardware blocks that are already on the die, not from squeezing more out of the core.

If you're picking silicon for a TinyML project, are you checking what accelerator hardware is already sitting unused on the chip you already chose?

<b>3. Post: Integration leap — Ambiq just gave an MCU a coprocessor whose only job is to not be the AI core</b>
Two Cortex cores. Same package. Deliberately different jobs.

Ambiq's new Apollo510 Lite pairs a 250MHz Cortex-M55 with Helium DSP/AI extensions — the part doing your inference — with a second, dedicated 48/96MHz Cortex-M4F coprocessor whose entire purpose is offloading wireless and sensor-fusion work so the AI core never gets interrupted by housekeeping.

That's a meaningfully different design philosophy than the usual "one core, context-switch between everything" MCU. Splitting AI-DSP workload from radio/sensor housekeeping onto physically separate cores is the kind of heterogeneous-compute partitioning that used to be reserved for flagship application processors — now it's showing up on a wearables-class part.

<b>5. Post: Physics-meets-architecture — 2.8 microamps is the number that actually decides your battery life</b>
Peak efficiency numbers make the datasheet. Quiescent current decides how long your device actually lasts.

ROHM's new BD83070GWL buck-boost converter delivers 97% peak conversion efficiency at 200mA load — a good number, but not the interesting one. The interesting number is 2.8µA: that's what the chip draws with no load at all, sitting idle, which is where most battery-powered sensor nodes spend the overwhelming majority of their life.

Automatic PFM/PWM switching is what makes both numbers true at once — PWM for efficiency under real load, PFM for near-zero draw at idle — packed into a 1.2×1.6mm WLCSP. For anything coin-cell or energy-harvesting powered, idle current dominates the battery-life equation far more than peak efficiency does.

Next time you're sizing a power rail, which number are you actually optimizing for?
