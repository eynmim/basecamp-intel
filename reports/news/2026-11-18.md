<b>═ 🔥 TOP STORY ═</b>
Espressif shipped Arduino-ESP32 3.3.13 on 17 Nov. It moves the stable Arduino core from ESP-IDF v5.5.5 to v5.5.6+. That rebase matters more than the feature list. ESP-IDF's own advisories name v5.5.6 as the patched release for the lwIP DNS-cache stack overflow (CVE-2026-113783, CVSS 7.4), and v5.5.5 as affected, so Arduino users on 3.3.12 had no stable way to get that fix until yesterday. The release also hardens WebServer header validation, rejects slashes in suffixed URI arguments, bounds DNS question parsing to the UDP packet, and stops a full AsyncUDP queue from locking the lwIP task. The release notes do not label any of this as a security fix; that the CVE fix comes in through the IDF rebase is our reading of the two advisories. Why it matters: on Arduino, the framework version decides which IDF CVEs you carry, so 3.3.13 is the first stable Arduino core without the DNS-cache overflow.

<b>═ 🔒 EMBEDDED CYBERSECURITY ═</b>
• <b>lwIP DNS cache overflow: an NTP pool can crash the device on its own</b> [High] — In ESP-IDF's dns_lookup(), the cached-lookup path copies every cached address into the caller's buffer without checking its size. Callers such as SNTP pass a single ip_addr_t. It triggers only when CONFIG_LWIP_DNS_MAX_HOST_IP is 2 or more (the default is 1), and the advisory notes that a legitimate multi-record hostname such as an NTP pool can crash a device even without an attacker. Fixed in v6.0.3 and v5.5.6; v5.4.5 and v5.3.7 were not yet released when the advisory came out, and v5.2 gets no fix. <a href="https://github.com/espressif/esp-idf/security/advisories/GHSA-ch63-jxm5-vmvf">Source →</a>
• <b>Bluedroid BLE Mesh GATT: a signed error code becomes a huge memcpy</b> [Medium] — In CVE-2026-113781 (CVSS 7.1), a negative ATT error returned by the read callback was stored in a uint16_t. The result was then used as a copy length from a small stack buffer. Exploiting it needs no pairing, only an exposed PB-GATT or Proxy bearer; NimBLE and v6.1+ are not affected, and the fix is in v6.0.3, v5.5.6, v5.3.6 and v5.2.8. <a href="https://github.com/espressif/esp-idf/security/advisories/GHSA-rjvf-fxv5-x87j">Source →</a>
• <b>Zephyr SOCKS5 client leaks up to 12 bytes of kernel stack</b> [Watch] — CVE-2026-95822 (Low, CVSS 3.3) was published on 17 Nov. socks5_tcp_connect() took the address type from the proxy's address family but read the bytes from the destination's, so an IPv6 proxy with an AF_INET destination reads past the IPv4 struct. It needs the opt-in CONFIG_SOCKS with both IPv4 and IPv6, and the fixes are in 4.3.2 and 4.5.0. <a href="https://github.com/zephyrproject-rtos/zephyr/security/advisories/GHSA-xvvw-v57r-7rwm">Source →</a>

<b>1. Post: Security wake-up — the NTP pool that crashes your device</b>
This ESP32 stack overflow can be triggered without an attacker. A normal NTP pool is enough.

Espressif published an advisory (CVE-2026-113783) for its lwIP port. When a hostname resolves to several addresses, the DNS cache stores all of them. On a later lookup, dns_lookup() copies every cached address into the caller's buffer.

The SNTP client passes a buffer with room for one address. The gethostbyname-style API has no length parameter, so the caller has no way to protect itself.

The bug stays hidden behind a non-default setting: CONFIG_LWIP_DNS_MAX_HOST_IP has to be 2 or more. The first resolution goes to the network and works. The second one, served from the cache, overflows. It passes a quick bench test and fails in the field.

When did you last diff your sdkconfig against the defaults and ask why each change is there?

<b>2. Post: Code-review lesson — one uint16_t, one remote overflow</b>
A negative number stored in a uint16_t is now a BLE CVE.

In ESP-IDF's Bluedroid BLE Mesh adapter (CVE-2026-113781), the GATT read callback returns a signed length, where a negative value means an ATT error. The handler stored it in an unsigned 16-bit variable.

So a failed read did not look like an error. It looked like a length close to 64 KB, which was then passed to memcpy from a small stack buffer. A nearby device could trigger it without pairing, through the provisioning or proxy bearer.

The insight is that the API mixed error codes and lengths in one return value, and the bug sat at the type boundary. -Wsign-conversion would have flagged that assignment.

Do you build your firmware with -Wconversion on, or is the warning noise too high to keep?

<b>3. Post: Tooling reality check — your Arduino version is your CVE list</b>
On Arduino-ESP32, you don't choose your ESP-IDF version. The core version you install chooses it for you.

Arduino-ESP32 3.3.13 shipped yesterday, based on ESP-IDF v5.5.6+. The previous stable release, 3.3.12, was built on v5.5.5.

That matters because ESP-IDF's own advisories list v5.5.5 as affected and v5.5.6 as patched for a DNS-cache stack overflow. The Arduino release notes don't mention the CVE. They just say "IDF v5.5.6".

So "I'm on Arduino, I don't track IDF advisories" is not a safe position. Each Arduino release is a snapshot of precompiled IDF libraries, with its CVEs included.

<b>4. Post: Protocol-design lesson — two sources of truth, one leak</b>
Zephyr's SOCKS5 client took the address type from one struct and the address bytes from another.

The advisory (CVE-2026-95822), published yesterday, is rated Low, but the pattern is worth knowing. socks5_tcp_connect() chose IPv4 or IPv6 encoding based on the proxy's address family. It then read the destination address using that size.

With an IPv6 proxy and an IPv4 destination, it read 16 bytes from an IPv4 structure, up to 12 bytes past its end. In CONFIG_USERSPACE builds that was kernel stack, sent to whoever runs the proxy.

The opposite case is memory-safe but quietly connects to the wrong host.

The fix is the general rule: get the type and the data from the same object, and reject a length that doesn't match.

Where in your code does one variable describe another variable's layout?

<b>5. Post: Regulatory shift — the first CRA standards don't give you conformity</b>
The first horizontal EN 40000 parts for the EU Cyber Resilience Act are about to be published, and on their own they won't make a product presumed compliant.

EN 40000-1-1 (vocabulary) and -1-2 (principles of cyber resilience) completed formal approval this autumn. Their exact publication date is still unconfirmed.

A harmonised standard only gives presumption of conformity once it is cited in the Official Journal. Trackers report that -1-2 is not planned for citation. The part expected to be cited first is -1-3, on vulnerability handling, and it is still in approval.

For firmware teams, the practical work is in that third part: SBOMs, advisory intake, coordinated disclosure, signed updates. The principles document describes it, and -1-3 is the part expected to require it.

Is your team building the vulnerability-handling process now, or waiting for the cited text?
