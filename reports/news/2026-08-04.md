<b>═ 🔥 TOP STORY ═</b>
CISA disclosed CVE-2026-14227 on July 30: an insufficient session-expiration flaw in MikroTik RouterOS's API service that lets an attacker with only low-privilege API access extract the router's WireGuard private key in plaintext. Because the API doesn't properly expire sessions, a single low-privilege foothold is enough to pull key material that should never leave the device — turning what looks like a minor access-control bug into full VPN impersonation and decryption of all associated WireGuard traffic. RouterOS runs on hundreds of thousands of routers used as VPN endpoints for exactly the kind of remote lab and field-device access embedded engineers rely on. CISA's guidance is blunt: disable remote API access where it isn't strictly needed, since there's no indication a config-only mitigation fully closes the gap otherwise. Why it matters: it's a reminder that "just an API session bug" and "your VPN's root secret is gone" can be the same finding — worth checking whether any router you use for remote access to hardware has its API surface exposed to begin with.

<b>1. Post: Security wake-up — a session bug that leaks your VPN's root secret</b>
A router forgetting to expire an API session sounds minor. It's not — it just handed out a plaintext WireGuard private key.

CISA disclosed CVE-2026-14227 on July 30: MikroTik RouterOS's API service doesn't properly expire sessions, so an attacker with only low-privilege API access can extract the device's WireGuard private key in plaintext. That key is supposed to never leave the router.

The interesting failure here isn't cryptographic — WireGuard itself is fine. It's that an access-control bug one layer up gave an attacker a path straight to the key material the crypto was supposed to protect. Defense in depth exists precisely for cases like this, and here it evidently didn't.

If you use a router as a VPN endpoint for remote access to lab hardware or field devices, do you know whether its management API is reachable from outside your trusted network right now?

<b>3. Post: Physics-meets-architecture — the process node is the feature</b>
An 800MHz Cortex-M85 inside a microcontroller isn't a core story. It's a silicon-process story.

STMicroelectronics' new STM32V8 is the company's first STM32 built on an 18nm FD-SOI process, a departure from the bulk CMOS nodes prior generations used. That process choice is what lets ST push a Cortex-M85 to 800MHz while keeping power draw inside what a microcontroller is supposed to consume.

It's a useful reminder that the core you pick off Arm's IP catalog is only half the performance story — the fab process underneath decides how far that core can actually be pushed before power and thermals say no. Same core, different node, different product category.

Next time a new MCU family launches, do you check the process node before the clock speed?

<b>5. Post: Regulatory shift — the cybersecurity bar for EU radio products isn't waiting for the CRA</b>
Everyone's watching the Cyber Resilience Act's 2027 deadline. The rule that's actually being enforced on wireless products right now dates back to August 2025.

Since August 1, 2025, the EU's Radio Equipment Directive Delegated Act has required radio equipment sold in the EU to meet network-security, data-protection and fraud-prevention requirements — satisfiable via the harmonised standards EN 18031-1/-2/-3. The CRA will eventually supersede RED's cybersecurity provisions, but not until it fully applies in December 2027.

For anyone building or shipping a wireless embedded product into the EU today, RED — not the CRA — is the compliance bar that actually matters right now. It's easy to fixate on the bigger, later deadline and miss the one already live.

If you're designing for the EU market, is RED's EN 18031 already part of your compliance checklist, or is it still a CRA-shaped blind spot?
