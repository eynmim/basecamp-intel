<b>═ 🔥 TOP STORY ═</b>
The Zephyr Project published a batch of security advisories on September 9 spanning three unrelated subsystems: a Bluetooth Classic L2CAP receive-path flaw that dispatches inbound data to channels stuck in CONNECTING/CONFIG state before authentication completes (CVE-2026-15460), an ext2 filesystem driver bug where a crafted image's oversized block count drives the bitmap scanner roughly 512 MB past its buffer (CVE-2026-13478, plus a related divide-by-zero on mount), and a type-confusion bug in the Sierra Wireless HL78xx GNSS NMEA0183 driver caused by a struct layout mismatch between where match state is initialized and where the parser callbacks read it (CVE-2026-15461). All three are fixed in Zephyr v4.4.2. None of them are exotic radio-range exploits — they're the kind of state-machine and bounds-checking mistakes that live quietly in mainline for years until someone fuzzes the right code path. Why it matters: if you've ever treated an upstream RTOS release as "someone else already audited this," this is the reminder that mainline Zephyr still ships this class of bug in Bluetooth, filesystem, and driver code simultaneously.

<b>1. Post: Security wake-up — three CVEs, three unrelated subsystems, one RTOS</b>
An RTOS you might already be shipping just got three unrelated security bugs fixed in the same point release — Bluetooth, a filesystem, and a GPS parser, all broken in completely different ways.

Zephyr's September 9 advisories cover a Bluetooth Classic L2CAP handler that processed data on channels stuck in CONNECTING state before authentication finished, an ext2 driver where a crafted image's oversized block count drove a bitmap scanner about 512 MB past its buffer, and a GNSS NMEA0183 driver where a struct field was one position off from where the parser expected it — a classic type-confusion bug hiding in plain sight.

None of these are exotic. They're the ordinary mistakes — a missing state check, an unvalidated length field, a struct layout assumption — that live in mainline code for years until someone finally fuzzes that exact path. All three are fixed in v4.4.2.

If your BOM includes an RTOS, when did you last actually check its CVE feed instead of assuming "stable" means "audited"?

<b>2. Post: Regulatory shift — the EU's vulnerability-reporting clock now applies to what you already shipped</b>
As of yesterday, if your connected product is already sitting on shelves in the EU, you now have 24 hours to report an actively exploited vulnerability in it — not just for products you release from now on.

The EU Cyber Resilience Act's Article 14 reporting duty went live on September 11 through ENISA's new Single Reporting Platform: a 24-hour early warning, a 72-hour technical notification, and a 14-day final report for actively exploited vulnerabilities, all routed to your national CSIRT and ENISA. Critically, this covers products already on the market, not only newly placed ones.

The part that changes how you build, not just how you respond: knowing what to report in 24 hours means knowing exactly what's in your firmware right now — which pushes SBOM discipline from "nice to have" to a hard prerequisite, retroactively, for anything you've already shipped.

If a CVE landed in one of your dependencies tomorrow, could you produce an accurate component list for it in under 24 hours?

<b>3. Post: Integration leap — the modem does the inference now</b>
The chip that used to just move your data over the cellular network can now also decide, on its own, whether that data is worth sending.

Telit Cinterion's new edge AI SDK embeds Google's LiteRT (formerly TensorFlow Lite) directly into the Linux-based firmware of upcoming 4G, 5G RedCap, and high-performance 5G cellular modules, shipping Q4 2026. Standard .tflite models — trained on a normal PC or even a Raspberry Pi — load straight onto the module with no external AI accelerator and no companion MCU.

This collapses a system that used to need three separate parts — sensor MCU, inference accelerator, cellular modem — into one, for the specific case of models small enough to fit LiteRT's footprint. That's a real architecture simplification for cost-sensitive cellular IoT, not just a marketing bullet.

Would you trust an inference result running on hardware you can't easily instrument for debugging?

<b>4. Post: Tooling unlock — the debug probe workflow that quietly replaced OpenOCD</b>
A lot of embedded developers are still writing OpenOCD config files for a job a single Rust binary now does better.

probe-rs bundles flashing, a GDB server, a VS Code debug extension, and a standalone CLI into one actively maintained toolkit for ARM and RISC-V targets over common debug probes. It's matured to the point where, for a growing share of workflows, it's the practical default instead of hand-rolled OpenOCD scripts.

The real win isn't speed, it's surface area: one tool, one config format, one thing to keep updated across flashing and debugging, instead of stitching together OpenOCD, a separate GDB server, and probe-specific quirks for every new board.

If you're still maintaining an OpenOCD .cfg file for a Cortex-M or RISC-V target, what's stopping a probe-rs trial on your next board bring-up?

<b>5. Post: Physics-meets-architecture — 18 microamps per megahertz, running real code</b>
18 microamps per megahertz. That's the active-mode current draw of a real, programmable Cortex-M0 core — not a sleep-mode number, a running number.

e-peas' EDMS105N, described as the lowest-power Cortex-M0 commercially available, is a 32-bit, 24 MHz MCU built for exactly this: sensor nodes where the power budget comes from a harvester, not a battery you can swap.

The interesting part isn't the headline current figure — it's what it implies architecturally. When active-mode power gets this low, "wake briefly, compute, sleep" duty cycles stop being a workaround for a power-hungry core and start being unnecessary; you can just leave more of the pipeline running longer per harvested joule, which changes how you'd actually structure the firmware.

Where's the line, in your own designs, between optimizing sleep current and just picking a core that doesn't need to sleep as aggressively?
