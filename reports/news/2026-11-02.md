<b>1. Post: Integration leap — QUIC on a microcontroller RTOS</b>
HTTP/3 and SSH now ship inside an RTOS that runs on a Cortex-M.

Zephyr 4.5.0 landed this week with QUIC and HTTP/3, an RTP stack and an SSH server and client in the tree.

Those were Linux-class features until recently. The engineering question is no longer "can the stack run" but "what does it cost in flash, RAM and timers, and does it fit next to my radio stack". The release also adds SPDX 3 SBOM generation, so the same build can describe what it contains.

I would profile it on a mid-range part before believing any slide.

<b>2. Post: Security wake-up — a boot feature switched off</b>
Sometimes the safest fix is turning the feature off.

ESP-IDF 5.3.6 and 5.2.8 disabled ECDSA Secure Boot V2 on ESP32-H2, C5 and P4, citing a vulnerability in that flow.

Secure boot is the root of every other guarantee: signed OTA, flash encryption, attestation. If the root scheme is weak, everything stacked on it inherits the weakness, and a shipped device can't change its ROM.

The practical lesson is to record which scheme each product revision uses, so an advisory is a lookup, not an archaeology project.

Do you track your boot-chain choices per hardware revision?

<b>3. Post: Regulatory shift — the CRA clock</b>
11 December 2027 is a firmware deadline, not a legal footnote.

That is when the main obligations of the EU Cyber Resilience Act apply. RED cybersecurity rules for radio products have applied since August 2025, and the harmonised standard tracks IEC 62443-4-2 closely.

For engineers this turns into concrete work: SBOMs, vulnerability handling, secure update paths. Zephyr 4.5 now generates SPDX 3 SBOMs in-tree, which shows where toolchains are heading.

Teams that start now treat it as a build-system task. Teams that start in 2027 treat it as a fire drill.

<b>4. Post: Tooling unlock — a small API that removes a classic bug</b>
Drift in periodic tasks is a bug most of us have written at least once.

FreeRTOS-Kernel V11.3.1 added <code>xTaskPeriodicDelay</code> for periodic tasks, along with <code>uxTaskCallForEachTask</code> and <code>configIDLE_AFFINITY</code> for pinning idle tasks to cores.

The same release brought SMP support to Armv8-M ports. Small APIs matter as much as big ones, because they replace hand-rolled timing code that quietly drifts.

I would grep an old codebase for loops that compute their own wake times and see what could be replaced.

What is the oldest timing workaround still living in your firmware?

<b>5. Post: Capability unlock — NPUs inside ordinary MCUs</b>
An NPU is becoming a line item on a microcontroller datasheet, not a separate chip.

TI's TinyEngine NPU is in the MSPM0G5187, available in production quantities, with the AM13E23019 in preproduction and more variants due by the end of 2026.

Once inference hardware sits on a general-purpose MCU, the design question changes. It is less "which accelerator do I add" and more "which model fits the memory and power budget I already have".

That favours engineers who can profile and quantise, not only train.
