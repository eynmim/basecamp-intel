<b>═ 🔥 TOP STORY ═</b>
ESP-IDF v5.5.6 shipped on 16 Oct with vulnerability fixes in the Bluedroid L2CAP parser (added buffer-length check), the TEE (secure-service arguments from the normal world are now copied into TEE memory before use) and upstream Wi-Fi supplicant patches. <b>1. Post: Security wake-up — secure boot flow switched off</b>
Espressif quietly disabled a secure boot mode on several chips.

ECDSA Secure Boot V2 is now disabled on H2, C5, P4 and some preview SoCs across recent ESP-IDF point releases. The release notes cite a vulnerability in that flow and point to the Chip Errata for details.

The lesson for me: a signed-boot feature on the datasheet is not the same as a signed-boot feature you can ship. I now check errata before locking a design to a boot scheme.

Do you re-read errata when you choose a secure boot scheme, or only after a CVE lands?

<b>2. Post: Regulatory shift — CRA reporting is live</b>
Since September, shipping connected firmware in the EU comes with a reporting clock.

Secondary sources put the start of Cyber Resilience Act vulnerability and incident reporting at 11 Sep 2026, with full obligations in Dec 2027. I would confirm the exact dates in the Official Journal text.

For firmware engineers this means traceability: which library version shipped in which build, and who triages the CVE. That is an engineering problem before it is a legal one.

<b>4. Post: Tooling unlock — migrating to ESP-IDF 6.1</b>
The big ESP-IDF 6.1 change is not a feature; it is what gets moved out.

MQTT is now a component-manager package, mbedTLS jumps to 4.1.0 and drops a 192-bit curve, and the ESP32-P4 default revision becomes v3.0. Each is small alone, but together they break builds that looked fine on 5.5.

I treat a major IDF bump as a dependency audit first and a feature hunt second.

<b>5. Post: Physics-meets-architecture — trust at the world boundary</b>
ESP-IDF v5.5.6 now copies secure-service arguments into TEE memory before running them.

The release notes give only the fix. My reading, not Espressif's words: it closes the gap where the normal world could change an argument after the secure side validated it, a classic time-of-check to time-of-use pattern.

Isolation only helps if data crossing the boundary is snapshotted. Pointers across worlds are a smell.

Where do you copy versus share across trust boundaries?
