<b>═ 🔥 TOP STORY ═</b>
CVE-2026-64573, added to NVD on August 5, sits in the Linux kernel's Qualcomm Bluetooth NVM firmware parser (drivers/bluetooth/btqca.c). Inside qca_tlv_check_data(), the TLV bounds check subtracts a fixed size_t constant from an attacker-controlled signed length; if that length is under 12 bytes, the subtraction wraps to a huge unsigned value and the parser writes a 12-byte struct past the end of a vmalloc'd firmware buffer during Bluetooth controller bring-up. CVSS 3.1 rates it 7.0 (High), and because Qualcomm Bluetooth silicon ships across laptops, routers, and embedded Linux boards, this is a supply-chain-wide patch item, not a niche one. The fix landed upstream in July but distro and vendor propagation lags behind the kernel.org commit as usual. Why it matters: it's a textbook integer-underflow bug hiding in firmware-parsing code nobody audits — the exact class of bug worth checking for in any custom BLE/BT stack code you write yourself.

<b>1. Post: Security wake-up — the filesystem library under half your embedded stack has six open CVEs</b>
Six memory-corruption bugs, one filesystem library, and it's running inside more of your toolchain than you think.

runZero disclosed seven CVEs in FatFs — the FAT/exFAT filesystem code embedded in ESP-IDF, STM32Cube, Zephyr, MicroPython, ArduPilot, RT-Thread, and Mbed. A crafted USB or SD card image can trigger integer overflow, buffer overflow, or divide-by-zero conditions during mount.

The part that should change how you think about it: only one of the seven — a denial-of-service bug — has an upstream fix. The other six, including the memory-corruption ones, are still open. If your project reads untrusted storage media, "wait for the patch" isn't a strategy right now.

If you're shipping ESP32 or STM32 firmware that mounts SD cards, have you actually checked which FatFs version you're pinned to?

<b>2. Post: Physics-meets-architecture — a harvesting chip that cold-starts on 1.5 microwatts</b>
275 millivolts. That's all it takes to wake this chip up from zero.

The AEM15820 is a single-chip energy-harvesting IC that integrates both low- and high-power boost converters with MPPT and a cold-start threshold of just 1.5µW, built for hybrid indoor/outdoor photovoltaic cells.

The interesting design choice isn't the low threshold by itself — it's collapsing what used to be a multi-PMIC harvesting front-end (separate cold-start, boost, and MPPT stages) into one part. Fewer components between a dead cell and a working system means fewer failure points in exactly the scenario — total discharge — where a harvesting design is most fragile.

Would a single-chip harvesting front-end change how you'd budget board area on a wearable or energy-autonomous sensor design?

<b>3. Post: Price-floor shift — Wi-Fi 6 and BLE on one module for about two dollars</b>
Wi-Fi 6 used to mean a premium module. Espressif just priced it at roughly the same tier as a basic BLE-only part.

The ESP32-C61-MINI-1/1U strips the ESP32-C6's 802.15.4 radio, keeps a single RISC-V core, Wi-Fi 6, and BLE, and ships full ESP-IDF v6.0 support — landing around $2 per module at volume.

What's worth noticing: dropping 802.15.4 (Zigbee/Thread) isn't a downgrade for most designs — it's Espressif correctly betting that most cost-sensitive IoT products only ever needed Wi-Fi and BLE, and charging accordingly. That's a meaningfully lower BOM floor for any Wi-Fi-connected sensor node that doesn't need a mesh radio.

<b>5. Post: Tooling unlock — one TinyML runtime now targets Cortex-M, RISC-V, and NPUs from a single API</b>
Choosing a TinyML runtime used to mean picking one hardware backend and living with it. That's no longer true.

LiteRT — TensorFlow Lite's successor — hit general availability with TensorFlow 2.21, adding NPU acceleration and native PyTorch/JAX model conversion. LiteRT for Microcontrollers now covers Cortex-M, Tensilica HiFi, ARC, and RISC-V, with backend support spanning Arm Ethos-U, NXP eIQ, and ST X-CUBE-AI.

The real unlock is portability, not raw speed: a model built in PyTorch can now land on an MCU without a manual export-and-hope conversion step, and the same runtime targets very different silicon without a rewrite. That collapses a real chunk of the "which framework, which chip" decision tree edge-AI projects usually get stuck on early.

If you're scoping an edge-AI project this year, is runtime portability across chip families now worth more to you than squeezing the last few percent of inference speed?
