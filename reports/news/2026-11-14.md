<b>═ 🔥 TOP STORY ═</b>
The refrigeration-controller attacks now have a published, one-request way in. CVE-2026-124004, published 12 Nov, is a hardcoded master password for the built-in Administrator account in Copeland (formerly Dixell) XWEB EVO supervisors before 5.6.2: a single login request with that credential returns a full admin session. VulnCheck rates it 9.3 (CVSS 4.0), and the product line reached end of service in March 2026. Upgrading also does not close every hole: CVE-2026-124012 is a daily-password authentication bypass for the same Administrator account in 5.6.2 through 5.8.8, and the same research bundle includes OS command injection and session bypass. CERT-FR's alert CERTFR-2026-ALE-012 reportedly names Copeland and Dixell XWEB among the compromised controller families. Current sources do not list either CVE as known exploited. Why it matters: a credential compiled into firmware cannot be rotated in the field, so a product line that is end of service with a shipped backdoor can only be taken off the internet.

<b>1. Post: Security wake-up — a password you can't change</b>
The fix for one backdoor in these refrigeration controllers ships with a second one.

CVE-2026-124004 is a master Administrator password hardcoded into Copeland XWEB EVO supervisors before 5.6.2. One login request gets you a full admin session. Upgrading to 5.6.2 removes it, but CVE-2026-124012 covers 5.6.2 through 5.8.8: an Administrator password derived from the date, so anyone who knows the scheme can compute it.

The engineering point: a secret compiled into firmware is not a credential. It is a constant. You can't rotate it, revoke it or scope it, and this product line reached end of service in March 2026.

If you need factory or service access, give each device its own credential at provisioning, and make the vendor's own access expire.

Where does your team's service-access credential actually live?

<b>2. Post: Physics-meets-architecture — NPUs hit the memory wall</b>
Adding an NPU to a microcontroller doesn't help much if the weights can't get to it fast enough.

A new arXiv benchmark of ten sub-watt edge devices, including STM32N6, Alif Ensemble E7/E8 and GAP9, finds that the NPU-equipped MCUs are limited by memory rather than compute. Against a 1 GHz Cortex-M85, the NPU advantage ranges from 1.4x to 8.2x depending on the model.

That range tells you something. The NPU delivers its headline TOPS only when the model's working set fits close to the accelerator. Once tensors spill to external memory, the bus sets the speed and the MAC array mostly waits.

So for TinyML parts, read the SRAM size and bus bandwidth before the TOPS figure.

Do you choose edge AI silicon by TOPS or by memory?

<b>3. Post: Capability unlock — a desktop on FreeRTOS</b>
Someone built a desktop with a window manager on FreeRTOS, for chips that can't run Linux.

Sylphide OS 0.1 targets boards with no MMU: the Olimex ESP32-P4-PC, the Raspberry Pi Pico 2 and FabGL. On top of FreeRTOS it adds keyboard, mouse, display, storage and network drivers, a window manager and a desktop. Storage and networking are still unfinished.

It is a hobby project, but it makes a real point. With no MMU there is no process isolation, so every "app" shares one address space. Any desktop OS on this hardware works more like a 1980s home computer than like Linux, with the same benefits and the same risks.

For firmware engineers it is also a readable reference for building a multi-window UI on an RTOS.

Would you trust an MMU-less "desktop" with a network stack?

<b>4. Post: Tooling unlock — an SDR on an ESP32</b>
Many ESP32 radios can hand you raw I/Q samples. The function is just undocumented.

The ESP-SDR project uses it, and a new Adafruit guide runs it on the ESP32-C6 co-processor of the Metro ESP32-P4. The result is a 2.4 GHz software-defined receiver made from a part most of us already have in a drawer.

Why it matters for firmware work: most BLE and Wi-Fi debugging stops at the HCI or packet-sniffer level. Raw I/Q lets you look underneath that, at timing, interference and what the air actually looked like when a connection dropped.

It won't replace a lab SDR, but as a first look at the RF layer it's hard to beat on price.

<b>5. Post: Security wake-up — the factory reset that undid security</b>
A factory reset is supposed to make a device safer. On some Lenovo servers it brought back the default root password.

CVE-2026-81936: on ThinkSystem V4 XClarity Controller 3 firmware 2.51 through 2.56, resetting the XCC restored the default OpenBMC root password. Lenovo found it in an internal review and says it has changed its process to catch this kind of regression.

The lesson goes well beyond servers. Reset paths get far less testing than boot paths, yet they rewrite the most security-critical state on the device. Every IoT product that supports reset needs a test that runs the reset and then checks that no default secret came back.

Does your CI ever factory-reset a real device?
