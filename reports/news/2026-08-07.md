<b>═ 🔥 TOP STORY ═</b>
Security research firm Binarly disclosed six vulnerabilities in U-Boot's FIT (Flattened Image Tree) signature-verification code, tracked as advisories BRLY-2026-037 through BRLY-2026-042. Two of the six enable arbitrary code execution during firmware-signature verification itself, while the other four crash the bootloader via an out-of-bounds read, a null-pointer dereference, unvalidated externally-stored data, and unbounded recursion; no CVE identifiers have been assigned yet. The affected code paths have existed since U-Boot v2013.07, meaning more than 50 stable releases and countless vendor forks — routers, industrial gear, IoT devices, and server Baseboard Management Controllers all commonly boot through U-Boot — are potentially exposed to a malicious FIT image delivered over a compromised update channel or exposed recovery port. Why it matters: "Secure Boot enabled" and "verification code audited" turned out not to be the same claim — a decade-old signature-checking path was attackable at the image-parsing layer, not the cryptography, which is exactly the class of bug a code review focused on key management would miss.

<b>1. Post: Security wake-up — secure boot's weak point wasn't the crypto</b>
Six new bugs in U-Boot don't touch a single cryptographic key. They break secure boot anyway.

Binarly's BRLY-2026-037 through 042 sit in U-Boot's FIT image signature-verification code — the parser that checks a firmware image before trusting it. Two of the six let an attacker execute code during that check; the other four crash the bootloader outright. The vulnerable paths have existed since U-Boot v2013.07, meaning over 50 stable releases and every vendor fork built on top of them.

The lesson isn't "patch U-Boot," it's where secure boot actually breaks in practice. Everyone threat-models the key management and the signing pipeline. Almost nobody audits the code that parses the image before the signature check even runs — and that's exactly where a decade-old bug hid.

If your secure boot chain has a code review, has anyone looked at the parser, or only the keys?

<b>2. Post: Capability unlock — one inference runtime, four architectures, no rewrite</b>
ONNX Runtime 1.28 quietly closed a gap that used to mean separate build targets for separate silicon.

The release adds ARM64 2-bit weight kernels for aggressive quantization, RISC-V RVV INT8 GEMM/GEMV kernels, and Linux sysfs-based NPU discovery that follows the kernel's new accel-device subsystem instead of a vendor-specific API. Put together, a model deployment pipeline can now target ARM64 CPUs, RISC-V cores, and Linux-hosted NPUs through the same runtime interface.

The quiet part is the sysfs NPU discovery — it means ONNX Runtime doesn't need a hand-written driver integration per NPU vendor anymore, it just walks the standard accel device tree the kernel already exposes.

<b>5. Post: Tooling unlock — a one-line config change closes a secure boot gap</b>
ESP-IDF v5.5.5 doesn't add a feature. It turns off one that was quietly broken.

The release disables the ECDSA-based Secure Boot V2 path on ESP32-H2, ESP32-C5, and ESP32-P4 specifically, patches a JPEG-decoder overflow reachable from a malformed image, and adds a new config option — CONFIG_SPIRAM_ENC_EXEMPT — that lets you exempt specific PSRAM regions from encryption instead of an all-or-nothing setting.

The Secure Boot V2 fix is the one worth stopping for: if you shipped Secure Boot V2 on any of those three chips before this release, the ECDSA path you were relying on is exactly what got disabled, meaning the actual protection you thought you had may not have matched what your config claimed.

If you've got Secure Boot V2 enabled on an H2, C5, or P4 project, have you pulled v5.5.5 and re-checked which signing path is actually active?
