<b>═ 🔥 TOP STORY ═</b>
Two new reports say Arduino-ESP32 3.3.13 broke the native USB Serial/JTAG port (HWCDC) on the ESP32-S3, and both trace back to the same change, PR #13048. In issue #13141 (19 Nov), the reporter shows that #13048 enables the IN-token interrupt in HWCDC::begin() and never turns it off. A host that holds the port open polls the IN endpoint all the time, so the chip takes one interrupt per token. Measured loop() throughput at 80 MHz dropped from 58,495 to about 46,000 iterations per second (about 21 % less), and a UART reading 8 KB at 230400 baud lost about 1.7 KB to FIFO overflows. Issue #13137 (18 Nov) is a second failure: if the host writes before Serial.begin(), RX stops for good until the ROM bootloader runs. The fix proposed for it, PR #13138, is still open and has had no maintainer review. No maintainer has replied to #13141 either, so both diagnoses are the reporter's for now. Why it matters: any S3 sketch on 3.3.13 that logs over native USB while also running a UART, audio or camera pipeline loses about a fifth of its CPU, and the symptom looks like a bug in your own code.

<b>═ 🎯 BOTTOM LINE FOR ALI ═</b>
• <b>Action:</b> If any S3 project of yours (Life_logger, camera sketches) builds on Arduino-ESP32 3.3.13 and logs over native USB, pin 3.3.11 until #13138 merges and someone answers #13141. On the INMP441 I2S pipeline, a 20 % CPU loss is enough to cause dropped audio frames.
• <b>Skill:</b> Run the #13141 benchmark yourself: count loop() iterations with the serial monitor open and closed. It takes 15 minutes, gives a real number, and makes a good interview story about how to measure an interrupt-load regression.
• <b>Skill:</b> Check P2CAM-style BLE code against the Elecbrakes failure. Every characteristic that triggers a physical action should need an encrypted, authenticated link (in NimBLE, the _ENC/_AUTHEN flags on the characteristic) plus a bond check in the callback.
• <b>Watch:</b> The ESP32 I2C ISR storm (290k entries/s after a late NACK) is a pattern ESP-IDF drivers can have too. If a sensor board ever drains the battery without crashing, count interrupts before you blame the sleep code.

<b>1. Post: Security wake-up — the brake command needed no pairing</b>
A trailer brake controller would accept braking commands from any Bluetooth device in range. It needed no pairing and no bond.

That is how secondary trackers describe CISA advisory ICSA-26-323-02 for Elecbrakes controllers: three critical BLE CVEs, one at CVSS 9.6, with the OTA update path also reported as vulnerable. A firmware fix is reported as available.

What gets me is that BLE already has the tools for this. A GATT characteristic can require an encrypted, authenticated link before a write is accepted. The stack enforces that before your callback ever runs. Leaving it out is a design decision, often made early to make the mobile app "just connect".

Bluetooth security here is mostly attribute permissions and bonding policy, not cryptography.

For anything that moves metal, what is your rule: authenticated link only, or app-layer auth on top?

<b>2. Post: Tooling unlock — the 20 % you didn't know you were paying</b>
One added interrupt cost an ESP32-S3 about 21 % of its loop throughput, but only while the serial monitor was open.

A bug report against Arduino-ESP32 3.3.13 traces it to the native USB serial driver. It now enables the "IN token received" interrupt to detect an open host, and never turns it off. A host that holds the port open polls that endpoint all the time, so the chip takes one interrupt per poll.

The reporter's numbers: 58,495 loop iterations per second on 3.3.11 and about 46,000 on 3.3.13. A UART reading 8 KB at 230400 baud lost about 1.7 KB to FIFO overflows.

The quiet lesson is that your debug connection is part of the system you're measuring. Benchmark with it attached and detached, or you're measuring the cable.

Do you profile firmware with the debug port open?

<b>3. Post: Physics-meets-architecture — 290,000 interrupts a second</b>
One uncleared status bit after a late I2C NACK, and an ESP32 entered its interrupt handler about 290,000 times a second until someone pulled the power.

That is one of four fixes in a Zephyr I2C driver backport merged this week. The handler cleared the controller's interrupts only on READ or WRITE status. A NACK that arrived late left TRANS_COMPLETE set, so the ISR fired again forever.

The same patch masks interrupts around the RX FIFO read on the original ESP32, following the chip's DPORT errata. Without that, an interrupt landing mid-read could return an empty-FIFO value as real data.

Errata are not footnotes. They are the place where silicon timing and driver structure meet, and a driver that ignores them works on the bench and fails in the field.

When did you last read the errata sheet for the MCU you ship?

https://github.com/zephyrproject-rtos/zephyr/pull/126194

<b>5. Post: Regulatory shift — less time between standard and law</b>
The EU has reportedly given its standards bodies three more months to deliver some Cyber Resilience Act standards. The law's main deadline did not move.

Trackers report a Commission implementing decision adopted on 10 November that extends the delivery dates for some horizontal and all product-specific CRA standards. The main obligations for products with digital elements still apply from 11 December 2027.

For firmware teams, the arithmetic is uncomfortable. The documents that give presumption of conformity, such as vulnerability handling and the product-category standards, will now arrive later, and the time between "the standard exists" and "the law applies" gets shorter.

The practical response is to build the processes the standards will describe now: SBOMs, a vulnerability intake path, signed updates, a support-period policy. Map them onto the standard text when it lands.

Is your team building CRA processes now, or waiting for the final standards?
