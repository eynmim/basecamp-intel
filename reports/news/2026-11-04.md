<b>1. Post: Security wake-up — the hash that forgot a field</b>
A secure-boot check can pass while hashing less than you think.

CVE-2026-46728 affects U-Boot before 2026.04. The hash for FIT image verification left out the hashed-nodes field, so signature verification could be bypassed.

The lesson isn't U-Boot-specific. A signature only protects the bytes that went into the hash. Anything outside that coverage is unauthenticated, however solid the crypto looks.

When did you last audit exactly which bytes your bootloader authenticates?

https://aviatrix.ai/threat-research-center/new-u-boot-flaws-could-enable-stealthy-firmware-attacks-2026/

#embeddedsystems #cybersecurity #firmware #embedded

<b>2. Post: Tooling unlock — ESP-IDF 6.0 changes the defaults</b>
ESP-IDF 6.0 quietly changed the C library under your firmware.

Picolibc replaces Newlib as the default, PSA Crypto replaces the legacy MbedTLS APIs, and compiler warnings are now errors by default.

Legacy ADC, DAC and I2S drivers are gone too. If you have audio code on the old I2S API, the migration is real work, not a version bump.

Treat warnings-as-errors as a gift: it surfaces latent bugs before the field does. Has anyone measured the footprint change with Picolibc yet?

https://www.espressif.com/en/news/ESP_IDF_6.0

<b>5. Post: Regulatory shift — security is now a ship requirement</b>
In the EU, firmware security stopped being optional.

The RED cybersecurity delegated act became mandatory on 1 August 2025, with EN 18031 as the harmonised route. The Cyber Resilience Act's main obligations follow on 11 December 2027.

For engineers this means threat models, update mechanisms and secure boot become design inputs, not afterthoughts. Compliance knowledge is becoming a hiring differentiator.
