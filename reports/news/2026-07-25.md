<b>1. Post: Security wake-up — the maintainer who never wrote back</b>
A single unresponsive maintainer is standing between three weeks of public disclosure and every ESP32 board that reads an SD card.

runZero disclosed seven bugs in FatFs — the tiny FAT/exFAT library bundled into Espressif ESP-IDF, ST's STM32Cube, Zephyr, MicroPython, and ArduPilot — on July 1. The headline bug is a CVSS 7.6 integer overflow in the FAT32 mount path. Only one of the seven got an upstream fix. The other six are still open.

The part that should worry anyone shipping firmware: runZero tried repeatedly to reach the maintainer, looped in JPCERT/CC, and got silence. FatFs isn't a niche dependency — it's the filesystem code running underneath boards most of us treat as "someone else's problem to secure."

If your firmware touches removable media, have you actually checked which FatFs version is bundled in your SDK?

<b>3. Post: Tooling unlock — the peripheral your SDK finally uses</b>
Your ESP32-S3 has a hardware HMAC peripheral built for exactly this job, and until this week almost no mainstream toolchain actually used it.

ESPHome 2026.7.0 adds opt-in NVS encryption that derives its keys at runtime from an HMAC key stored in an eFuse block — hardware-backed secret storage instead of a key sitting in flash. It pairs that with software anti-rollback for signed OTA images, and switches ESP32/nRF52 builds to native ESP-IDF and nRF Connect SDK toolchains by default.

The interesting bit isn't the feature list — it's that this is a textbook implementation of "secure storage plus anti-rollback OTA," the exact pattern EU radio-equipment cybersecurity rules already expect from connected devices. If you're on bare ESP-IDF instead of ESPHome, the diff is worth reading as a reference implementation.

Anyone else's provisioning flow still storing secrets in plain NVS?

<b>4. Post: Physics-meets-architecture — 600x without touching the clock</b>
600 times more machine-learning throughput, and ST didn't touch the clock speed.

STM32N6 gets its ML performance from the Neural-ART Accelerator, a dedicated NPU delivering 600 GOPS alongside an 800MHz Cortex-M55 core. A paper published July 21 documents a teaching platform built around it for engineering coursework and competitions — real evidence this silicon is landing in classrooms, not just data sheets.

The lesson generalizes past this one chip: once general-purpose core scaling stops buying you much, the architecture answer is a fixed-function accelerator next to the core instead of a faster core. That's the same story behind every recent MCU-class NPU announcement this year — TI's TinyEngine, Nordic's nRF54LM20B — it's becoming the default MCU shape, not a premium option.

<b>5. Post: Regulatory shift — a 24-hour clock, a decade-old bug</b>
In 47 days, EU law requires 24-hour vulnerability disclosure. The bootloader running on millions of devices has bugs dating to 2013 and no CVE numbers assigned yet.

Binarly found six flaws in U-Boot — the bootloader underneath home routers, smart cameras, and a huge share of embedded Linux hardware — all triggered during signature verification of a boot image, two of them leading to code execution before the signature check even finishes. The vulnerable code has existed since v2013.07 across 50+ stable releases. Patches merged in June, but the July release had already frozen in April, so the fix waits until October.

The EU Cyber Resilience Act's Article 14 mandates 24h/72h incident reporting starting September 11. That clock assumes a supply chain that can actually produce timely reports — U-Boot and FatFs, both foundational and both currently stuck between disclosure and fix, are a live test of whether that assumption holds.

Does your BOM's incident-response plan account for dependencies with no formal security process at all?
