<b>═ 🔥 TOP STORY ═</b>
FreeRTOS-Kernel disclosed two security advisories on Aug 21 that hit its two hardware-isolation mechanisms at once. CVE-2026-77234 (CVSS 8.8, GHSA-w3vr-pr75-5hc6) is improper validation in the software-timer command path: on MPU-enabled ARMv7-M/ARMv8-M ports, an unprivileged task can submit a timer command that makes the privileged timer-service task execute a caller-supplied function — arbitrary code execution in privileged kernel context, bypassing MPU task isolation entirely. CVE-2026-77236 (CVSS 7.3, GHSA-vq2f-9qj3-jj2m) is a companion bug in TrustZone secure-context allocation: missing size validation lets a non-secure task request an undersized secure stack, corrupting adjacent secure-heap structures. Both affect FreeRTOS-Kernel back to V7.0.0/V10.2.0 respectively and are fixed only in V11.3.1. Why it matters: these aren't obscure subsystems — configENABLE_MPU and TrustZone are exactly the features an STM32L5/U5 or any Cortex-M FreeRTOS design turns on specifically to get hardware task isolation, so a project relying on that isolation for its security story needs to update now, not on the next convenient release cycle.

<b>1. Post: Security wake-up — the exact features you enable for hardware isolation just broke it</b>
Turning on FreeRTOS's MPU support is supposed to stop one task from touching another's memory. This week, it stopped stopping that.

CVE-2026-77234 (CVSS 8.8) is improper validation in FreeRTOS-Kernel's software-timer command path: on MPU-enabled ARMv7-M/ARMv8-M ports, an unprivileged task can submit a timer command that makes the privileged timer-service task execute a caller-supplied function — arbitrary code execution in kernel context. A companion bug, CVE-2026-77236, does something similar to TrustZone secure contexts, corrupting the secure heap when a non-secure task requests an undersized stack. Both are fixed only in V11.3.1.

The detail worth sitting with: neither bug is in application code. Both are in the isolation mechanism itself — the thing a design turns on specifically to contain a compromised task. When the isolation boundary is the vulnerability, "sandbox the untrusted code" stops being a mitigation until you patch.

Are you tracking FreeRTOS-Kernel CVEs the same way you'd track any other dependency, or does "it's the RTOS" make it invisible?

<b>3. Post: Capability unlock — a small LLM now runs on a Raspberry Pi 5 at real conversational speed</b>
99 tokens per second isn't a benchmark you'd expect from a device that costs less than a decent multimeter.

Google published official LiteRT-LM benchmark numbers for Gemma 4 E2B running on a Raspberry Pi 5: 99 tok/s prefill, 9 tok/s decode, with a peak memory footprint of just 1432 MB — all on CPU, via the XNNPACK delegate. That decode rate is roughly reading speed for a human, on hardware that ships for the price of a nice lunch.

The number worth internalizing isn't the raw throughput, it's the memory ceiling: 1.4 GB peak means this fits comfortably on an 4GB Pi 5, no swap, no accelerator card. That changes the calculus for edge deployments that were previously "needs a cloud round-trip" by default — a local assistant, a document summarizer, a voice interface — because the hardware to run it locally is now something you'd buy for a hobby project anyway.

<b>4. Post: Price-floor shift — 24-bit ADC precision just landed on an entry-level Cortex-M23</b>
24-bit sigma-delta ADCs used to mean "precision instrumentation part, premium price." That line just moved down a tier.

Nuvoton's new NSC128L42 is a 49.152 MHz Cortex-M23 with 320 KB flash and 18 KB SRAM — an entry-level part by any measure — that integrates a 24-bit sigma-delta ADC alongside a 12-bit SAR ADC, an LCD driver, and a 0.35 W Class-D speaker driver, all in one package aimed at blood-pressure monitors and precision scales.

The BOM insight: 24-bit resolution used to justify reaching for a dedicated precision ADC IC next to a cheaper MCU. Having that resolution built into an entry-tier MCU removes a component, a set of matching traces, and a calibration step from the design — the kind of integration that quietly reshapes what "cheap medical-grade measurement device" costs to build.

<b>5. Post: Regulatory shift — the EU's hardware security deadline everyone building for Europe needs on their calendar</b>
Six days from now, the EU's Cyber Resilience Act reaches its first real technical deadline — and most embedded teams I talk to haven't looked at it yet.

Aug 30, 2026 is when the CRA's core Type A harmonised standards — covering secure development practices and vulnerability handling — are due for delivery, with the vertical Type B standards following Oct 30. The Commission just published its first application guidance (July 27) specifically to help smaller manufacturers navigate this, ahead of full essential-requirements compliance landing Dec 11, 2027, backed by fines up to €15M or 2.5% of global turnover.

The part worth flagging for anyone shipping CE-marked hardware: this isn't a "big company" regulation. It applies to any product with digital elements sold in the EU, and the Sept 11 vulnerability/incident-reporting mandate that follows it means having a CVE-disclosure process isn't optional anymore — it's a compliance requirement with a clock on it.
