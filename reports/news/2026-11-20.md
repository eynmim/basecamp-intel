<b>═ 🔥 TOP STORY ═</b>
The first European standards written for the Cyber Resilience Act are out. CEN and CENELEC announced EN 40000-1-1 (vocabulary) and EN 40000-1-2 (cybersecurity principles, product risk management and lifecycle activities) on 19 Nov. The Commission gives 18 Nov as the publication date. This settles the date question from yesterday's report. Both are horizontal standards under standardisation request M/606, but CEN-CENELEC's project records mark both "no citation expected" in the Official Journal. Following them therefore does not by itself give presumption of conformity. That is still expected only from later parts such as prEN 40000-1-3 on vulnerability handling, and from the product-specific standards. Why it matters: from today, "CRA-aligned" in a job ad or a product datasheet has a concrete reference document, and its risk-management and lifecycle terms are the vocabulary EU embedded employers will use until the main CRA obligations apply on 11 Dec 2027.

<b>1. Post: Regulatory shift — the first CRA standard isn't the one that counts</b>
The first European standards written for the Cyber Resilience Act were published this week, and following them won't give you presumption of conformity.

CEN and CENELEC released EN 40000-1-1 (vocabulary) and EN 40000-1-2 (principles, product risk management, lifecycle activities). Their own project records say neither is expected to be cited in the Official Journal.

For firmware teams that changes how you read them. They are a shared dictionary and a process frame, not a compliance shortcut. The parts with real legal weight are still coming: vulnerability handling (prEN 40000-1-3) and the product-specific standards.

So the practical move is to adopt the vocabulary now, in threat models, update policies and SBOM notes, so the mapping is cheap when the harmonised parts land before the main obligations apply in December 2027.

<b>2. Post: Security wake-up — your GATT service is open on links you didn't accept</b>
A Bluetooth Mesh node can crash from a write on a connection its own server never accepted.

Zephyr's Mesh Proxy and PB-GATT servers set up per-connection state only for links that pass their accept checks: peripheral role, default identity, service registered. But the GATT services themselves were reachable on every link, including one the node opened as central.

A write on such a link reached state that was never initialised, which meant NULL dereferences in the Proxy receive path and in beacon sending. The fix is one rule: return -ENOTCONN from the Data In and CCC write handlers for any connection the server did not accept.

The lesson goes beyond Mesh. In BLE, a service being reachable and a connection being valid for it are two separate facts, and your write callback has to check both.

How many of your GATT callbacks assume the conn_handle is one they set up?

<b>3. Post: Tooling unlock — fuzzing seven lengths on your laptop</b>
The best part of a small Zephyr security fix this week was its test, not the fix.

The bug: the mcumgr SMP client read an 8-byte header before checking the buffer was at least 8 bytes long. That is a classic early read of stale memory.

The regression test sends every truncated length from zero to seven bytes through the function, in a host build (native_sim) with AddressSanitizer turned on. If anything touches a byte it shouldn't, ASan fails the test on the developer's machine, with no board, debugger or flaky hardware repro.

That is the step-change for firmware teams. Parsing code that never touches a register can run on the host under sanitizers, and boundary cases cost a few lines of loop.

Do you run any of your firmware's parsers under ASan, or does everything get tested on target?

<b>4. Post: Capability unlock — Wi-Fi at microamp idle</b>
2.44 µA asleep, 8 µA while staying associated to a 5 GHz access point. Those are Nordic's listed figures for its new nRF7120 module.

For years the advice for battery devices was simple: Wi-Fi to the cloud means a big battery or a short life, so use BLE to a gateway. The listed DTIM10 numbers (14 µA at 2.4 GHz, 8 µA at 5 GHz) put an associated Wi-Fi link in a current range that used to need a BLE gateway.

The engineering catch is in that "DTIM10". The device wakes for every tenth beacon, so idle current is a negotiation with the access point's configuration, not just the chip. Your latency budget and the customer's router settings now set the battery life.

Certification is still listed as planned, so this is a 2027 design decision, not a today one.

Would you drop a BLE gateway from your architecture for this?

<b>5. Post: Integration leap — a RISC-V MCU designed for the 2040s</b>
Infineon's first RISC-V automotive MCU platform samples in 2027 and is planned for volume around 2029–2030. That means firmware written for it will still be in service in the 2040s.

AURIX RC1 targets real-time control for software-defined vehicles and robotics. It is also designed for a production run of more than a decade.

That timeline is the real story for embedded engineers. In automotive, the ISA choice is a 15-year support commitment, and a vendor makes that bet only when it believes the toolchains, safety-qualified compilers and RTOS ports will still be there.

If RISC-V is now trusted for long-life safety-critical control, the skills gap shifts. Knowing how to bring up, debug and certify on RISC-V is no longer a side interest.
