<b>═ 🔥 TOP STORY ═</b>
Zephyr published two more WireGuard security advisories on Aug 28, extending its security-advisory wave into a sixth straight week. The more serious, CVE-2026-13734 (CVSS 6.5), sits in wg_process_data_message(): peer-state changes — endpoint roaming, liveness timers, keypair rotation — get committed before the anti-replay check runs, so an attacker who captures one valid encrypted packet and replays it from a spoofed address can redirect the tunnel's traffic before the replay check rejects it. The companion bug, CVE-2026-13735 (CVSS 3.7), let any 16-byte "keepalive" transport packet skip Poly1305 authentication entirely, letting an on-path attacker forge connection-state events with no valid key. Both affect Zephyr 4.4.0–4.4.1 and are already fixed — in 4.4.2, which shipped Aug 7, three weeks before either advisory was published. Why it matters: for anyone running Zephyr's WireGuard stack (common in constrained VPN/mesh gateways), the pattern from this whole advisory wave keeps repeating — the fix ships quietly in a point release, and the CVE explaining why you needed it arrives weeks later.

<b>1. Post: Security wake-up — a VPN bug where the state changed before the check that was supposed to gate it</b>
The order of two operations, three lines apart, is the entire vulnerability here.

Zephyr's WireGuard implementation updates a peer's roaming endpoint, liveness timers, and keypair rotation state — then checks whether the packet that triggered all that was actually a valid, non-replayed message. An attacker who captures one legitimate encrypted packet and replays it from a spoofed address gets the state changes applied before the replay check has a chance to reject anything. CVSS 6.5.

The generalizable lesson: "validate then act" isn't a style preference, it's the whole security property. Any code path that mutates trusted state has to treat that mutation as provisional until the check downstream of it actually passes — not just correctly implement the check somewhere in the function.

Where in your own protocol code does a side effect happen before the validation that's supposed to gate it?

<b>3. Post: Capability unlock — Google just open-sourced the missing standard for tiny AI chips</b>
Every cheap AI accelerator chip has its own incompatible way of being programmed. Google just tried to end that.

Coral NPU, announced this week with Google Research and DeepMind, is a fully open, RISC-V-based neural-processing architecture: a scalar core for control logic, a 128-bit SIMD vector engine, and a dedicated matrix engine for the actual neural-network math — targeting roughly 512 GOPS at a few milliwatts, aimed at hearables, AR glasses, and always-on ambient sensing.

The real unlock isn't the performance number, it's the openness. Fragmented, closed NPU toolchains are the reason "add AI to a $3 sensor" has stayed hard — every chip needs its own compiler and driver stack. An open reference architecture any silicon vendor can implement is what turns tiny on-device AI from a per-chip science project into something you learn once.

Would a shared open NPU architecture actually get silicon vendors to converge, or does everyone still differentiate at the toolchain layer?

<b>4. Post: Physics-meets-architecture — 1.1 microamps is what "always listening" actually costs now</b>
1.1 microamps. That's roughly what it costs, in sleep current, for a Bluetooth chip to sit ready to wake up at any moment.

Silicon Labs' new BG2B, unveiled this month, claims that sleep-current figure as its lowest yet — while also packing in Channel Sounding (Bluetooth's precise distance-ranging feature) and automotive CAN-FD support on the same silicon. It's still in early customer engagement, with production hardware slated for 2027.

The physics worth noticing: ranging and always-on listening used to trade off against each other, because both cost power budget on constrained silicon. Squeezing sleep current down that far while adding a compute-heavier feature like Channel Sounding means the power budget freed up elsewhere in the design — not that ranging got free.

For a battery-powered BLE design, would sub-2µA sleep current change what you'd consider "always on"?

<b>5. Post: Regulatory shift — the EU's big CRA deadline arrives tomorrow with nothing to actually comply against</b>
Aug 30 is the EU Cyber Resilience Act's first hard compliance gate for "important" Type A products. It arrives with zero harmonized standards published in the Official Journal — for any category.

The one real movement: on Aug 13, ETSI opened public enquiry on 17 final-draft product standards covering CRA's Annex III categories, from routers to connected toys, with comment windows closing between mid-September and mid-November. That's the standardization pipeline actually turning, just nowhere near finished.

The pattern worth internalizing for anyone entering EU-regulated hardware: a compliance deadline in a regulation and the technical standards you'd use to demonstrate compliance are drafted on separate, uncoordinated timelines — and the gap between them is where a manufacturer's actual engineering judgment calls have to fill in.
