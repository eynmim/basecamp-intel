<b>2. Post: Security wake-up — the vulnerable code isn't in your server, it's in your firmware's SSH client</b>
The bug isn't in the server you expose. It's in the SSH client sitting inside your firmware, waiting to talk to a server you don't control.

CVE-2026-55200 is a CVSS 9.2 heap overflow in libssh2's packet-length handling — but the twist is direction. A malicious SSH server can hand your device a crafted response and get code execution on it, no auth and no interaction beyond the connection your firmware already makes for updates or telemetry.

Most embedded threat models still treat the server side as trusted infrastructure and the device as the thing you defend. This flips that. And because libssh2 gets statically linked into router, NAS, and industrial-controller firmware, each vendor's bundled copy is a separate patch that has to happen on its own.

If your firmware dials out anywhere over SSH, do you actually know which libssh2 version is baked into the image you shipped?

<b>3. Post: Regulatory shift — the paperwork window just opened for who polices IoT security labels</b>
The US just opened filing for who gets to police IoT security labels.

On Aug 11 the FCC opened the window for organizations to become Cybersecurity Label Administrators under the U.S. Cyber Trust Mark program — the voluntary shield-logo label for consumer IoT devices meeting baseline security requirements. ioXt Alliance is already the Lead Administrator.

Voluntary today doesn't mean voluntary in three years. The EU's Cyber Resilience Act followed the same arc: harmonized-standards drafting first, then a hard reporting deadline this September. Watching how fast the US administrator ecosystem stands up is a decent leading indicator for how fast "nice to have" IoT security becomes "can't ship without it."

Which matters more to you as a device maker: a voluntary US label, or the EU's mandatory reporting clock?

<b>4. Post: Tooling unlock — Rust is about to stop being an LLVM-only language</b>
Rust has one real compiler backend today. That's about to change for anyone targeting a GCC-only architecture.

gcc-rs is a from-scratch reimplementation of the Rust language as a native GCC front end, and it's working toward compiling the official Rust test suite. Right now, rustc is fundamentally an LLVM frontend — if your target architecture doesn't have solid LLVM support, Rust simply isn't an option.

GCC supports a long tail of embedded architectures LLVM has never bothered with. A working gcc-rs doesn't make Rust faster or safer than it already is — it makes Rust possible on hardware where it currently isn't an option at all, which is a bigger unlock for embedded specifically than for any other Rust use case.

Is Rust-on-GCC worth tracking now, or a check-back-in-two-years project? 🦀
