<b>1. Post: Security wake-up — The bugfix release with a Bluetooth fix</b>
The most important line in a point release is often the one that says "parsing".

ESP-IDF v5.5.6 shipped with security fixes in Bluetooth L2CAP parsing and in TEE argument handling. Nothing about it is marketed as a headline feature.

The insight: protocol parsers and trusted-world interfaces are where memory-safety bugs live. Both take input from a boundary you do not control, and both are hard to cover with application tests.

Do you read changelogs for security lines, or only for new features?

<b>2. Post: Tooling unlock — A minor SDK bump that is not minor</b>
ESP-IDF v6.1 is called a minor update over v6.0, yet it moves esp-mqtt to the component manager and renames GPIO functions.

It also previews support for ESP32-S31, so one toolchain now spans a new part and the chips already in products.

The practical lesson: "minor" is a promise about versioning, not about your dependency graph. I would branch, build, and diff the config before trusting it.

How long does your team wait before adopting a new SDK minor?

<b>3. Post: Regulatory shift — Disclosure is now part of the job</b>
Since 11 September, EU manufacturers must report actively exploited vulnerabilities in their products.

That is the CRA reporting duty. The rest of the regulation applies from 11 December 2027, so the process arrives before the full compliance work.

For firmware engineers this makes vulnerability handling a design input: an SBOM, a way to push a patch, and a contact who can answer in hours.

<b>4. Post: Integration leap — Matter still runs on BLE</b>
Every Thread-based Matter device must also carry Bluetooth LE, because that is how a new device joins the network.

Matter 1.6, published in June, adds NFC-based setup, but BLE commissioning remains part of the picture for most devices. The stack you ship is really several radios' worth of firmware behaving as one.

For an engineer that means BLE provisioning bugs become smart-home onboarding bugs, which users blame on the product, not the protocol.

<b>5. Post: Physics-meets-architecture — The SPI bus is an attack surface</b>
A radio transceiver chip has its own firmware, and its host interface can be a way in.

CVE-2026-6232 is an out-of-bounds write in the Semtech LR11xx SPI host command interface. Exploiting it takes physical access and logical access to the SPI bus.

The insight: the peripheral next to your MCU is not a dumb pipe. It parses commands, so its length checks matter as much as yours do.

Do you treat peripheral firmware as part of your threat model?
