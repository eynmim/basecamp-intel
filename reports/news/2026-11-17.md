<b>═ 🔥 TOP STORY ═</b>
Espressif published ESP-IDF v6.1.1 on 16 Nov (tagged 13 Nov), and this bugfix release changes OTA behaviour. esp_https_ota now rejects plain-HTTP firmware downloads unless HTTP is explicitly enabled. Any OTA flow that used an http:// URL during development will now fail. The release also fixes Content-Length truncation in the HTTP server that allowed request smuggling. It adds a new Kconfig cap, HTTPD_MAX_REQ_BODY_LEN_KB, which defaults to 16 MB. Two other security fixes stand out: the TEE now copies REE-supplied secure-service arguments into TEE memory before acting on them, which closes a check-then-use window, and fixes from the upstream Wi-Fi supplicant have been ported. Breaking changes hit BLE Audio and ISO: addresses are now LSB-first, and some callbacks and getters have new signatures. Why it matters: ESP-IDF now applies a secure default in the OTA path by itself, so firmware teams that relied on plain-HTTP OTA during development have to opt in explicitly.

<b>1. Post: Security wake-up — the NULL pointer that doesn't crash</b>
On most Cortex-M chips, reading through a NULL pointer doesn't crash. It just returns data.

Zephyr published a Bluetooth host advisory this week (CVE-2026-93672). A connected peer can push an idle ATT channel into a lookup that dereferences a NULL request pointer.

The interesting part is the advisory's own impact analysis. On TrustZone non-secure, MMU targets or builds with null-pointer detection, it is a fatal reset. On a default Cortex-M build, address 0 is the vector table, so the read succeeds and the bug stays inert.

So the same line of C is a remote crash on one build and harmless on another. Your MPU configuration decides which.

Do you enable an MPU guard region at address 0 in your firmware, or only in debug builds?

<b>2. Post: Tooling unlock — OTA now refuses plain HTTP</b>
ESP-IDF v6.1.1 is a bugfix release, but one change will break some OTA setups.

esp_https_ota now rejects plain-HTTP firmware downloads unless you explicitly enable them. If your test rig serves images from an http:// dev server, the update fails after you upgrade.

I think this is the right default. OTA is the one path where the device runs code it got from the network, and "we'll add TLS before production" is how unauthenticated update endpoints end up in the field.

The same release fixes Content-Length truncation in esp_http_server (request smuggling) and adds a request-body size cap with a 16 MB default. On a chip with a few MB of PSRAM, you probably want that number much lower.

Did your SDK's secure default ever break a working build of yours?

<b>3. Post: Capability unlock — PyTorch on an MCU NPU, no heap</b>
ExecuTorch 1.6.0 removed dynamic allocation from its Arm Ethos-U backend.

That is a small line in the release notes with big consequences. In safety- and certification-minded firmware, malloc after init is often banned outright. An inference runtime that needs a heap is a non-starter there, however good its operator coverage is.

The same release hardens parsing of the Vela-compiled binary, adds SDPA decomposition and SAME-padding fusion for Cortex-M, and adds experimental streaming state kept inside the Ethos-U delegate, which is useful for audio or sensor windows.

Taken together, the PyTorch-to-MCU path is becoming practical for embedded production rather than just demos.

Is heap-free inference a hard requirement in your projects, or a nice-to-have?

<b>5. Post: Physics-meets-architecture — the union that crossed the syscall</b>
A C union with two function pointers in it just became a kernel privilege bug.

Zephyr's charger API passes properties as a union. Two members are notification callbacks. The user-mode syscall verifiers copied that union into the kernel without checking which property it was, so an unprivileged thread could hand the kernel any address to call (CVE-2026-91007, CVSS 7.8).

The max20335, pf1550 and bq2518x drivers then invoked that pointer from a supervisor-mode work handler on every cable plug or unplug. User mode got control flow at kernel privilege when someone plugged in a cable.

The fix rejects those two properties from user mode, and a BUILD_ASSERT forces a review whenever someone adds a new property.

Do your syscall or IPC boundaries ever pass structs that contain function pointers?
