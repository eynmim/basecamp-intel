<b>1. Post: Integration leap — a satellite modem is now a firmware update, not a new board</b>
Satellite connectivity used to mean a different radio, a different antenna, a different BOM line.

Nordic just shipped modem firmware that adds NB-IoT NTN — satellite connectivity under 3GPP Release 17 — to the nRF9151, a cellular IoT module already deployed in trackers and remote-monitoring designs with an application MCU, LTE-M/NB-IoT modem, and GNSS built in. No new silicon. The GEO/LEO satellite path arrives as a firmware capability on hardware that's already in the field.

The interesting part isn't "satellite IoT exists" — it's that coverage-gap tolerance, which used to be a hardware-selection decision made at BOM time, is becoming a software decision made at deployment time. That changes how you'd scope a remote-asset-tracking product: you can now ship one SKU and decide per-deployment whether satellite fallback is worth the data cost.

Would you design for satellite-fallback-by-default now, or still treat it as an opt-in feature flag?

<b>2. Post: Security wake-up — one 512-byte buffer, shared across every Bluetooth connection you have open</b>
A single shared buffer plus more than one open connection is a classic recipe for memory corruption. Zephyr's Bluetooth stack just proved it again.

CVE-2026-10660: the Broadcast Audio Profile Broadcast Assistant GATT client reassembled data from every connected peripheral into one file-static 512-byte buffer, while the busy flag and read offsets were tracked per-connection. Talk to two or more Scan Delegator peripherals at once, and their notification callbacks interleave on that shared buffer — writing past its end.

The bug pattern is the instructive part: per-connection state sitting next to a resource that was quietly shared across connections. It's an easy mistake to make in any multi-connection BLE role, and an easy one to miss in review because each connection's code path looks correct in isolation — the bug only exists in the interleaving.

If you're writing a multi-peripheral BLE central role, this is worth a five-minute audit of your own buffer scoping.

<b>4. Post: Physics-meets-architecture — a microcontroller that idles at 340 nanoamps and still keeps a clock running</b>
340 nanoamps. With a real-time clock still ticking and 8KB of SRAM still holding its contents.

e-peas demoed a complete battery-free IoT system: its EDMS105N MCU draws 18µA/MHz in active mode and drops to 340nA in its deepest sleep state — while retaining an RTC and 8KB of RAM — paired with its AEM15820 PMIC doing maximum-power-point tracking across hybrid indoor/outdoor photovoltaic cells to keep the whole thing charged.

The design insight is in what "sleep" means here: most ultra-low-power MCUs trade away RTC and RAM retention to hit their lowest sleep-current numbers. Keeping both alive at 340nA means the device can wake on a real-time schedule with full context intact, instead of re-initializing state from scratch on every harvested-energy wakeup — which is normally the actual power cost that kills battery-free designs.

<b>5. Post: Capability unlock — edge AI benchmarks just stopped pretending workloads are single-shot</b>
Most TinyML benchmarks measure one thing: classify this image, detect this keyword, done. Real agentic AI doesn't work that way.

MLCommons added an "Edge Agentic Inference" category to MLPerf Inference v6.1 — the first standardized benchmark for multi-turn, tool-calling LLM agents running on a single edge accelerator, instead of the single-shot detection/classification tasks edge benchmarks have measured until now.

The shift matters because tool-calling agents have a completely different performance profile than classifiers: state persists across turns, latency compounds across tool calls, and memory pressure builds instead of resetting every inference. Benchmarking that properly is what turns "can this edge board run an agent" from a marketing claim into a comparable number.

Worth watching which accelerators actually submit numbers once results start landing this quarter.
