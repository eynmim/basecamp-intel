<b>1. Post: Security wake-up — the bug that trusted its own I2C bus</b>
A Zephyr driver checked its buffer bounds — one instruction too late.

CVE-2026-14986 sits in the FIFO interrupt handler for Zephyr's ITE IT51xxx I2C target driver. It copies incoming host data into a fixed-size buffer, then checks whether the write index is still in bounds — after the write already happened. Any I2C master on the bus that streams past 256 bytes in one transaction drives the index straight through the buffer wall into adjacent device data.

The part that should bother you isn't the bug itself, it's the trust assumption underneath it: this runs in the target's kernel context, triggered by whatever else happens to share that bus. No software privilege needed, no network path — just a device that's a little too chatty, malicious or not.

If your firmware treats "on-board bus" as synonymous with "trusted," this is a good week to reconsider that.

<b>2. Post: Tooling unlock — Python just stopped treating RISC-V as an afterthought</b>
CPython spent months running on real RISC-V silicon before it was allowed to call itself "officially supported."

RISC-V just became a Tier 3 platform in CPython — the same continuous-testing tier every other serious target gets. The RISE Project loaned dedicated RISC-V buildbots so contributors could chase architecture-specific bugs on physical hardware instead of hoping emulation caught everything.

Here's the part that actually matters for firmware work: Tier 3 isn't a community patch that might rot next release. It's tested on every CPython change, which means the host-side tooling, test scripts and CI you'd want to build around a RISC-V MCU target now has a language runtime that won't quietly break under it.

If you've been defaulting to Arm purely because "the tooling is more solid," that gap just got smaller.

<b>4. Post: Regulatory shift — the standard the CRA will actually point to is almost here</b>
The Cyber Resilience Act keeps getting discussed in the abstract. The standard that will make it concrete for industrial products lands this quarter.

CENELEC's technical committee is harmonizing EN IEC 62443-4-2 into a CRA-aligned amendment, A11:2026 — due for adoption by August 2026 — alongside a matching update to the -4-1 process-requirements standard. Once formally published, this pairing becomes the presumption-of-conformity route for security requirements on industrial and critical digital products under the CRA.

The detail worth remembering: today, following IEC 62443 alone still isn't automatically sufficient CRA evidence. The harmonized version is what closes that gap — and it's not published yet, which means the compliance target for anyone building CRA-scope hardware is still technically in motion.

If you're heading into EU embedded work, this is the standard to actually read, not just cite.

<b>5. Post: Integration leap — a Bluetooth spec became testable silicon</b>
A wireless spec isn't real engineering until someone can run a conformance test against it. Bluetooth LE HDT just crossed that line.

Rohde &amp; Schwarz and Realtek jointly validated what they're calling the industry's first test solution for Bluetooth LE High Data Throughput, pairing R&amp;S's CMP180 radio tester against Realtek's RTL8922D and RTL8773J chips. HDT itself raises BLE's ceiling from 2 Mbps to 7.5 Mbps without giving up the low-power profile that makes BLE worth using in the first place.

The interesting part is the sequencing: draft spec, then test methodology, then silicon you can actually certify against — in that order. That's the difference between a roadmap slide and something you can design a product around next year.

Where would an extra ~3.75x BLE throughput actually change a design you're working on — OTA updates, audio, or something else?
