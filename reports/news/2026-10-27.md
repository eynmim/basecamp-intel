<b>1. Post: Security wake-up — the field the signature forgot</b>
A signed boot image can still be forged if the signature never covered the part you care about.

CVE-2026-46728 in U-Boot (before 2026.04) is exactly that: the hashed-nodes field was omitted from the hash calculation, so FIT signature verification could be bypassed.

The insight for me is that "we verify signatures" is not a security claim until you can say what bytes the signature covers. Every secure-boot design review should list the signed fields explicitly.

Do you audit what your bootloader actually hashes, or just that a check exists?

https://nvd.nist.gov/vuln/detail/CVE-2026-46728

#embeddedsystems #cybersecurity #firmware #embedded

<b>2. Post: Tooling unlock — release notes as a security feed</b>
Three ESP-IDF release notes quietly disable the same feature on three chips.

ECDSA Secure Boot V2 is switched off on ESP32-H2, ESP32-C5 and ESP32-P4 in v5.3.6, v5.2.8 and v6.1, with the notes citing a vulnerability. The notes do not explain the details.

For anyone shipping on those chips this is a design decision, not a footnote: your secure-boot scheme may need to change before the product does.

How often do you read SDK release notes line by line before bumping a version?

<b>3. Post: Capability unlock — an NPU next to a Cortex-M33</b>
200 MHz Cortex-M33, 2.56 GOPS NPU, one MCU.

TI's AM13Ex pairs the M33 core with its TinyEngine NPU, and the MSPM0G5187 brings the same idea to a Cortex-M0+ part. Both were shown at embedded world in March 2026.

The engineering point is where inference lives: next to the control loop, on the same chip, without a separate accelerator on the BOM. That changes how you partition the firmware.

Would you run your next sensor classifier on an MCU NPU or keep it on the CPU?

<b>5. Post: Architecture lesson — snapshot before you check</b>
A one-line fix worth stealing: copy the arguments before you execute.

ESP-IDF v5.5.6 snapshots secure-service arguments in TEE memory before execution. The usual reason to do this is to stop a caller changing the data after validation.

If you have a trust boundary, validate the copy you will actually use, not the buffer the other side can still write to.

Where in your firmware do you validate data that someone else can still modify?
