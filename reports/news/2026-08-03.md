<b>═ 🔥 TOP STORY ═</b>
A critical stack buffer overflow in OpenWrt's DHCPv6 server (odhcpd) lets an unauthenticated attacker on the same network trigger root-level code execution with a single crafted DHCPv6 REQUEST packet sent to UDP port 547. CVE-2026-53921 (CVSS 9.8) stems from two independent overflow sites in the DHCPv6 IA-reply serialization path: crafted IA options leave too little room in a fixed 512-byte stack buffer before more reply data gets appended without a bounds check. A companion bug, CVE-2026-55606, causes a 2560-byte overread from a 128-byte buffer on every little-endian target OpenWrt ships for — x86, ARM-LE and MIPS-LE. OpenWrt shipped fixes in 24.10.8 and 25.12.5 on July 28, but odhcpd runs as root, and as the advisory notes, most embedded hardware lacks the stack canaries and ASLR that would otherwise blunt this class of bug. Why it matters: it's a textbook reminder that on constrained embedded targets, a single unchecked length field in a network-facing parser is still enough to hand an attacker root — the exact failure mode worth testing for in any firmware of yours that touches untrusted packets.

<b>1. Post: Security wake-up — one filesystem, everyone's stack</b>
One filesystem library, seven unpatched bugs, and it's already inside almost every microcontroller you've coded for.

runZero just disclosed seven vulnerabilities in FatFs — the small FAT/exFAT library that ships inside Espressif's ESP-IDF, STMicroelectronics' STM32Cube, Zephyr, MicroPython, ArduPilot and RT-Thread. The worst, CVE-2026-6682, is an integer overflow in the FAT32 mount code: bad math produces a false file size that later code trusts as a real read length, and on real hardware that path leads to memory corruption.

Here's the uncomfortable part: FatFs has one maintainer, who hasn't responded even after JPCERT/CC tried to coordinate disclosure. Only one bug got an upstream fix — the rest are now each downstream vendor's problem, on their own timeline.

If your board reads SD cards or USB drives, do you actually know which FatFs revision is baked into your SDK?

<b>3. Post: Regulatory shift — vulnerability reporting gets a deadline</b>
September 11, 2026 is now a hard date: reporting an actively exploited vulnerability in your EU-market embedded product becomes a legal obligation, not a courtesy.

The European Commission's new Cyber Resilience Act guidance, published July 27, runs past 80 pages of worked examples and flowcharts — what counts as "substantial modification," how to set a support period, how to run the required risk assessment. It lands ahead of the CRA's first hard conformity-assessment deadline (Type A products, August 30) and well before full application in December 2027.

For engineers, the interesting shift isn't the paperwork — it's that vulnerability disclosure and incident reporting are becoming part of a product's legal lifecycle, not just its changelog. If you're building anything that talks to a network and ships into the EU, "secure by design" just got a deadline attached.

<b>5. Post: Capability unlock — FreeRTOS reaches newer silicon</b>
FreeRTOS just added official MPU support for Cortex-R82 and Cortex-M52 — two Arm cores most embedded engineers haven't designed for yet — plus a new Arm China STAR-MC3 port.

The 202604 LTS release (kernel v11.3.0) also trims how many Memory Protection Unit regions FreeRTOS claims for itself, freeing hardware regions an application can reserve for its own memory protection — a small change with a real payoff on MCUs where MPU regions are scarce. coreMQTT v5.0.2 ships alongside it with full MQTT v5.0 support, including topic aliases that matter on bandwidth-constrained links.

None of this is flashy, but it's the unglamorous work that decides whether FreeRTOS is ready the day a design lands on newer silicon.
