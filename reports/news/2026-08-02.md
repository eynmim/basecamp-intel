<b>═ 🔥 TOP STORY ═</b>
A developer going by "slvDev" released esp32-ai, an open-source project that runs a 28.9M-parameter TinyStories language model directly on an $8 ESP32-S3 at roughly 9.5 tokens/sec. The trick isn't a smaller model — it's borrowing Google Gemma's Per-Layer Embeddings idea: a 25M-row embedding table (the bulk of the parameters) stays memory-mapped in flash and only ~6 rows (~450 bytes) are read per token, while a much smaller ~560K-parameter dense core runs from RAM at 4-bit quantization, fitting the whole 14.9MB model inside 16MB flash and 8MB PSRAM. It hit Hacker News on July 25 and passed 1,200 GitHub stars within three days. Why it matters: this runs on the exact chip most embedded engineers already prototype on, and the flash-as-parameter-store pattern generalizes to any embedding-heavy inference workload that doesn't fit in SRAM — not just LLMs.

<b>1. Post: Capability unlock — a language model fits on a microcontroller you already own</b>
A 29-million-parameter language model, running on an $8 microcontroller, at almost 10 tokens per second.

esp32-ai (by developer slvDev) does this on an ESP32-S3 by borrowing an idea from Google Gemma: instead of loading the full embedding table into RAM, it memory-maps a 25-million-row table straight from flash. Each token read pulls maybe 450 bytes off flash instead of holding megabytes in SRAM. What's left running from RAM is a tiny ~560K-parameter dense core, quantized to 4 bits.

The insight generalizes past LLMs: any time your parameter count is dominated by a big, mostly-static lookup table (embeddings, LUTs, codebooks), flash-as-storage plus a small hot RAM core might fit where "just shrink the model" doesn't.

Would you trust flash read latency in your own inference loop, or does this only work because token generation is already slow enough to hide it?

https://github.com/slvDev/esp32-ai

<b>2. Post: Security wake-up — an industrial protocol library had a pre-auth memory bug</b>
No login required. Just a crafted OPC UA message, and an out-of-bounds write on a device your factory floor trusts.

CISA's ICSA-26-211-08 covers four memory-safety bugs in open62541, the open-source OPC UA stack embedded in industrial and automation controllers worldwide. The worst is an integer overflow in array-dimension handling that's reachable pre-authentication in PubSub configurations — CISA flags Critical Manufacturing, Energy, and Transportation Systems as affected sectors.

The uncomfortable pattern: OPC UA was built for interoperability between vendors, which means one shared, widely-vendored library becomes a single point of failure across an entire industrial protocol ecosystem — the same shape of problem embedded engineers have already seen with FatFs.

If your stack vendors OPC UA anywhere, do you actually know which open62541 version is baked in?

<b>3. Post: Regulatory shift — the EU's first real CRA deadline just got a date</b>
Four weeks. That's how long EU manufacturers of "important" connected products have left before the Cyber Resilience Act's first conformity-assessment deadline hits.

Type A products under CRA Annex III must complete conformity assessment by August 30, 2026, with the more safety-critical Type B/C category following on October 30 — the first concrete compliance test since the Commission's application guidance landed a week earlier.

For engineers, not just compliance teams, this is the moment "secure by design" stops being a slide in a slide deck and starts being a gate a product has to pass through before it can ship into the EU market — worth understanding even as a student, because it will shape how firmware update and vulnerability-disclosure processes get designed from here on.

<b>4. Post: Integration leap — one radio, two smart-home protocols, running at once</b>
Zigbee and Matter-over-Thread, running concurrently on the same radio, in a bulb you can buy today.

Signify's upcoming Philips Hue firmware uses Silicon Labs' multiprotocol RCP architecture to run both protocols simultaneously instead of forcing users through a one-time, all-or-nothing migration between them.

The interesting part isn't the marketing pitch of "no migration needed" — it's the RF/scheduling engineering underneath: sharing a single 2.4GHz radio across two independent protocol stacks without one starving the other's timing requirements is a genuinely hard multiprotocol concurrency problem, and this is a shipping consumer answer to it.
