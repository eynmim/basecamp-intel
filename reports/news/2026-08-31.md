<b>═ 🔥 TOP STORY ═</b>
Zephyr shipped 4.4.2 on Aug 28 patching two bugs in its WireGuard implementation, and the more serious one is a different kind of mistake than the memory-safety bugs that dominated last week's advisory batch. CVE-2026-13734 (CVSS 6.5): wg_process_data_message() updates a peer's endpoint address, liveness timers, and keypair state right after AEAD decryption succeeds — but before wg_check_replay() runs — so an attacker who captures a valid ciphertext packet can replay it from a spoofed source address and hijack where the tunnel thinks its peer lives, even though the replay check ultimately rejects the packet. A second, lower-severity bug (CVE-2026-13735, CVSS 3.7) let forged 16-byte keepalive packets skip Poly1305 verification entirely via an early return, letting an attacker without the session key fake connection-status signals. Both live in the same function, in code well past Zephyr's early memory-safety era. Why it matters: "verify before you trust" failing on ordering rather than on a missing bounds check is a reminder that hardening one bug class doesn't retire the review checklist — it just moves the next mistake somewhere else in the same function.

<b>1. Post: Security wake-up — verify-before-trust, in the wrong order</b>
CVSS 6.5, and the vulnerable code sits inside the function meant to prevent exactly this.

Zephyr's WireGuard implementation just got patched (4.4.2) for a bug where decrypting a packet successfully happens before checking whether it's a replay — not after. In between those two steps, the code already updates the peer's known address, refreshes liveness timers, and promotes session keys.

So an attacker who's captured one valid encrypted packet can replay it from a different address, and even though the replay check eventually rejects the packet, the state changes it triggered along the way already happened. The fix was reordering two function calls — nothing structural.

The generalizable lesson: "decrypts successfully" and "is trustworthy" are not the same property, and any code that acts on the gap between them is exploitable regardless of protocol.

Where in your own connection-handling code does a side effect fire before the check meant to gate it?

<b>2. Post: Regulatory shift — the loophole closing inside your BOM</b>
Buying a "safe" module no longer means the chip inside it is safe.

The FCC's new equipment-authorization rule takes effect Sept 8: it closes what's been called the "component-part loophole." Until now, a restricted chipmaker's silicon could reach the US market legally as long as it was integrated into a module built by an unrestricted vendor — the finished module just needed its own authorization.

The new rule reaches inside the module. Any device incorporating a logic-bearing hardware component — an IC, sub-assembly, or module — sourced from a Covered List entity is now blocked from authorization, regardless of who assembled the final part.

The engineering implication: BOM due diligence now has to go one layer deeper than "which vendor sold me this module" into "whose die is actually on it" — information that hasn't traditionally been on a datasheet's first page.

Does your BOM tooling actually track die origin, or just module vendor?

<b>3. Post: Tooling unlock — Yocto codifies AI-code disclosure</b>
Yocto just made a formal rule out of something most open-source projects still argue about quietly.

The project's contributor guide now requires that patches written with AI assistance disclose that fact. A maintainer went further and dropped AGENTS.md files into bitbake and openembedded-core — machine-readable instructions telling coding agents themselves to follow the disclosure policy, not just human contributors.

This isn't about banning AI-written code. It's about the reviewer's actual problem: a subtly wrong patch from a human usually comes with a mental model you can interrogate in review comments; a subtly wrong patch from an agent might not, and knowing which you're looking at changes how carefully you need to read it.

Expect this to spread — Yocto is a widely-forked embedded Linux build system, and its contribution norms tend to become everyone else's eventually.

Does your own team's PR template ask whether AI wrote it?

<b>5. Post: Integration leap — Europe's open RISC-V server stack</b>
Ten server boards, up to four RISC-V chips each, and not a single proprietary interconnect between them.

The EU-funded RISER project published an update this week on its all-European RISC-V cloud server platform — a "microserver" architecture where up to ten boards interconnect over open, high-speed hardware interfaces, with storage and memory treated as shared resources any processor in the system can reach at low overhead, all running a fully open Linux software stack.

The integration leap isn't the RISC-V silicon itself — cores exist elsewhere. It's that the interconnect, the firmware, the OS, and the runtime are being co-designed as one open system instead of bolted together from whatever proprietary parts happened to be available, which is normally how server hyperconvergence gets built.

For anyone tracking EU tech-sovereignty efforts as a career signal: this is what a "sovereign compute stack" looks like when it's actually being built, not just funded.
