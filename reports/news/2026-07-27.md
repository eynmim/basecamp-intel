<b>═ 🔥 TOP STORY ═</b>
CISA disclosed CVE-2026-10577, a maximum-severity (CVSS 10.0) flaw in Rockwell Automation's 1715-AENTR redundant I/O EtherNet/IP adapter: a network-reachable debug port accepts intrusive CLI commands — read/delete files, kill tasks, modify memory, change I/O states — with zero authentication on firmware 3.003 and earlier. The affected units sit in energy, water, and critical-manufacturing deployments; Rockwell's fix is a firmware update to 3.011+, with no real workaround short of isolating the port at the network layer. It's a stark example of a full debug console left reachable from the production network path in a device shipping today, not a legacy relic. Why it matters: every embedded engineer builds some form of debug/service console into firmware — a UART shell, a JTAG-adjacent CLI, a diagnostic port — and this is a sharp reminder that "undocumented" is not the same as "unreachable," so debug interfaces need the same access control as the rest of the attack surface, by design.

<b>1. Post: Security wake-up — the debug port that scored a perfect 10</b>
CVSS 10.0 isn't a common score. This week one CVE earned it for the simplest possible reason: a debug port with no lock on the door.

CVE-2026-10577 hits Rockwell Automation's 1715-AENTR I/O adapter — a network-reachable debug CLI that accepts file deletion, task kills, memory writes, and I/O state changes with zero authentication, on firmware shipping in energy and water infrastructure right now.

The uncomfortable part: nearly every embedded project I've worked on has some version of this exact interface — a UART shell, a diagnostic port, a "just for bring-up" CLI. This bug is what happens when that interface makes it to production still open.

If your firmware has a debug console, when did you last check what happens when someone finds it who isn't you?

<b>2. Post: Integration leap — Docker, but for a microcontroller</b>
Sandboxed apps, OTA updates without a firmware reflash, one binary across three different vendor's silicon. That used to describe a server fleet, not an MCU.

AkiraOS layers a WebAssembly runtime on top of Zephyr RTOS, letting .wasm apps install, update, and crash in isolation from each other and from the kernel — each one only touching hardware it's explicitly granted. ESP32-S3, Nordic's nRF5x, and STM32 all run the same binary.

The interesting shift isn't the container metaphor, it's what it does to firmware release cycles: instead of "flash new firmware, hope nothing regresses," you get "push one app, sandbox catches the blast radius." That's a genuinely different failure model for OTA.

Would you trust a WASM sandbox with production firmware updates yet, or is native reflash still safer for your use case?

<b>3. Post: Regulatory shift — the compliance deadline nobody finished meeting</b>
The EU's cybersecurity rules for connected radio equipment became mandatory a year ago. The ecosystem is still catching up.

EN18031 has required NVS encryption, secure provisioning, and OTA-rollback protection on RED-covered devices since August 1, 2025. ESPHome's July 2026 release just shipped exactly that trio as its "first coordinated wave" toward compliance — a full year later.

The lesson isn't about ESPHome specifically, it's about how compliance actually rolls out in embedded: a legal deadline passes, and the real engineering work — retrofitting encryption and rollback protection into an existing, widely-deployed codebase without breaking it — takes many more months after that.

If you're building for the EU market, is your OTA path already rollback-protected, or still on the to-do list?

<b>4. Post: Capability unlock — a PMIC that starts on almost nothing</b>
275 millivolts. That's all it takes to cold-start e-peas' newest energy-harvesting PMIC — roughly what a single dim indoor solar cell puts out on a cloudy day near a window.

The AEM15820, now broadly stocked, pairs low- and high-power boost converters with maximum-power-point tracking so it can harvest anywhere from microwatt-scale indoor light to multi-watt direct sun with the same chip, switching converter paths automatically as input power scales.

What stands out is the range, not just the floor: most harvesting PMICs are tuned for one energy regime. Covering "dim indoor" through "bright outdoor" with a single part removes a design decision that used to force a choice between two different chips depending on where the product would actually live.

Would a single-chip PV harvesting range like this change how you'd spec a battery-free sensor node?

<b>5. Post: Price-floor shift — BLE goes back to entry-level</b>
Not every Bluetooth sensor needs a dual-core RISC-V coprocessor and a megabyte of flash. Nordic just shipped a chip for the ones that don't.

The nRF54LS05A and nRF54LS05B strip the nRF54L series down to a 128MHz Cortex-M33, a 4th-gen BLE radio, and 0.5MB of NVM — pin-compatible with their bigger siblings, but priced and sized for simple single-chip sensors and actuators where the full nRF54L15 feature set was always overkill.

The interesting part is the positioning, not the specs: it's an admission that "just use the flagship part for everything" was leaving cost on the table for the majority of BLE designs that never touch half the silicon they were paying for.

Does your next BLE sensor design actually need the full nRF54L15, or would an entry-level part like this cover it?
