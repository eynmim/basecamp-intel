<b>1. Post: Security wake-up — One length field, 254 bytes</b>
A single length field can turn a radio chip's SPI interface into a write primitive.

A recent CVE entry for the Semtech LR11xx describes an oversized length in a host command that lets 254 bytes be written past an internal buffer. It needs physical access and SPI-bus access, so it is not a remote bug.

The insight: we treat the bus between MCU and radio as trusted. On a board with a debug header or a hijacked MCU, that bus is an attack surface, and the radio's firmware parser is the last line of defence.

How do you validate length fields on your own host-command interfaces?

<b>2. Post: Security wake-up — The secure boot option Espressif turned off</b>
Sometimes the most informative release note is the feature that got disabled.

ESP-IDF v5.5.5, v5.3.6 and v5.2.8 all disable ECDSA Secure Boot V2 on ESP32-H2, C5 and P4, citing a vulnerability. Details are promised in the chip errata.

For anyone designing a secure boot flow, the takeaway is that the algorithm choice is a product decision, not a checkbox. Fallback options and key plans need to exist before a flaw lands.

<b>3. Post: Tooling unlock — Breaking changes as a feature list</b>
ESP-IDF v6.1 is a reminder that upgrading is engineering work, not a version bump.

The notes list esp-mqtt moving to the component manager and mbedTLS 4.1.0 dropping the 192-bit curve, with an HTTP server body size change in v6.0.3.

The useful habit: read the breaking-change list first, pin the toolchain, then re-run your hardware-in-the-loop tests on a branch. Each of those changes can hide in a build that still compiles.

<b>4. Post: Capability unlock — An NPU on a microcontroller</b>
TI claims up to 90x lower latency and 120x lower energy per inference with an NPU on the MCU.

Those are vendor numbers, announced in March with the MSPM0G5187 and AM13Ex families, so treat them as an upper bound against a no-accelerator baseline.

The part that interests me: TI says the NPU will spread across its MCU portfolio. If that holds, a model becomes a normal firmware dependency, and the questions become memory layout and power budgets instead of whether it fits.

<b>5. Post: Regulatory shift — Disclosure is now part of the job</b>
Since 11 September, EU manufacturers must report actively exploited vulnerabilities in their products.

That is the CRA reporting duty. The rest of the regulation applies from 11 December 2027, so the process comes before the full compliance work.

For firmware engineers this makes vulnerability handling a design input: an SBOM, a way to push a patch, and a contact who can answer in hours rather than weeks.
