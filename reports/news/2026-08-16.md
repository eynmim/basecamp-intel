<b>═ 🔥 TOP STORY ═</b>
The Zephyr Project disclosed four CVEs in a single Aug 13-14 batch, headlined by CVE-2026-12364 (CVSS 8.4): the kernel-mode logging syscall verifier forwards caller-supplied source, desc, and data pointers straight through without the mandatory K_SYSCALL_MEMORY_READ() boundary check, letting any unprivileged userspace thread read arbitrary kernel memory or crash the system on every release from v2.6.0 through v4.4.0 with CONFIG_USERSPACE and CONFIG_LOG enabled. The same batch fixes a Bluetooth GATT client denial-of-service (CVE-2026-12236, an unauthenticated peer can hang the BLE stack with a zero-stride Read-By-Type response), a LoRaWAN fragmented-transport out-of-bounds write (CVE-2026-12363), and an SMP-only work-queue use-after-free (CVE-2026-12365) that hits dual-core targets — like the ESP32-S3 — using k_work_delayable cancel/free patterns. All four are fixed in v4.4.2, shipped this week. Why it matters: this is a coordinated disclosure spanning kernel isolation, BLE, LoRaWAN, and SMP scheduling in one of the two RTOSes most embedded engineers will touch professionally — any Zephyr fleet with logging and userspace enabled needs to move to v4.4.2 now, not on the next convenient release cycle.

<b>1. Post: Security wake-up — a logging function just proved it can leak your entire kernel</b>
Four CVEs, one 24-hour disclosure window, and the bug at the center of it lives in the one code path every embedded project writes without thinking twice: logging.

Zephyr's kernel-mode logging syscall forwards caller-supplied pointers straight to the implementation without the mandatory boundary check (K_SYSCALL_MEMORY_READ) that CONFIG_USERSPACE exists to enforce. Any unprivileged userspace thread can use it to read arbitrary kernel memory or crash the box — CVSS 8.4, and it's been there since v2.6.0.

The same batch also fixed a Bluetooth GATT client DoS reachable by any unauthenticated peer, and an SMP-only work-queue use-after-free that only shows up under real dual-core concurrency, not single-core testing. That's the pattern worth remembering: the bugs that survive years of use are rarely in the exotic driver code, they're in the boring paths everyone trusts by default.

If you run Zephyr with userspace isolation and logging both on, have you checked you're past v4.4.2?

<b>5. Post: Integration leap — a $1 SIM card can now talk directly to your modem's application processor</b>
The SIM card was supposed to be the dumb, trusted part of a cellular design. Turns out it can push code straight into the modem.

Researchers found the GSM "Proactive SIM" feature — which lets a SIM card send an unsolicited RUN AT instruction to the host modem — enabled by default across many cellular IoT modules. On a Quectel EC25 modem inside an EV charger, this achieved code execution on the modem's own Linux application processor; the vendor confirms the RUN AT interface stays open by design.

What makes this worth sitting with is the trust direction: everyone models the SIM as something the modem authenticates against, not something that can reach back and execute on the modem itself. Any product pairing an MCU with a cellular module now has a second, less-obvious attack surface to threat-model — one baked into the GSM spec, not a single vendor's firmware bug.

If your design uses a cellular add-on module, does your threat model account for what the SIM itself can do to it?
