Espressif's ESP-IDF bugfix releases now disable ECDSA Secure Boot V2 on several chips because of a reported security issue. <b>1. Post: Security wake-up — the boot chain is the trust root</b>
Recent ESP-IDF bugfix releases quietly disable ECDSA Secure Boot V2 on several chips.

The release notes cite a security issue with ECDSA signing on those parts. Different chips are named in different releases, so the exact list is worth checking against Espressif's advisory.

The lesson for me is that a signature scheme is a choice you should be able to change. If your bootloader hard-codes one algorithm, a disclosure like this turns into a field recall.

How crypto-agile is your boot chain?

<b>2. Post: Security wake-up — six bugs before your OS even starts</b>
U-Boot picked up six reported vulnerabilities in July, several in FIT image signature verification.

That code decides whether the kernel image is trusted at all. A bug there means a malicious image can crash the device or run code at boot.

I would not wait for a distro update on a custom board. Check which U-Boot version your BSP pins and whether verified boot is actually enabled.

Do you know your U-Boot version without looking?

<b>3. Post: Capability unlock — a small NPU on a cheap MCU</b>
TI says its TinyEngine NPU cuts inference latency up to 90 times and energy per inference more than 120 times.

Those are vendor numbers against a baseline without the NPU, so treat them as a ceiling, not a benchmark. Still, they land on the MSPM0 line, which is a low-cost MCU family.

The interesting part is the target class. Edge AI on a low-cost part changes which sensing problems are worth solving on the device.

<b>4. Post: Regulatory shift — compliance becomes a skill</b>
The EU Cyber Resilience Act reaches full obligations on 11 December 2027.

Until then the RED cybersecurity rules under EN 18031 already apply to radio products. Incident reporting duties start earlier.

For firmware engineers that means secure boot, signed updates and a vulnerability-handling process are product requirements. I am treating them as core skills, not extras.

<b>5. Post: Integration leap — Thread border routers finally agree</b>
Since January, new Thread Border Routers must certify to Thread 1.4.

The practical change is that routers from different vendors can join one existing network instead of each creating its own.

For anyone building Matter-over-Thread devices, that removes a whole class of "works with brand A only" bugs from the test matrix.
