<b>═ 🔥 TOP STORY ═</b>
F5 disclosed a critical zero-day in BIG-IP Access Policy Manager, CVE-2026-94127 (CVSS 9.8), and CISA added it to the Known Exploited Vulnerabilities catalog on September 22 after confirming active exploitation. The flaw is a heap-based buffer overflow in APM's OAuth-profile handling: any virtual server pairing an APM access policy with an OAuth profile can be hit with crafted network traffic that corrupts heap memory and lets an unauthenticated attacker execute arbitrary code — from the data plane, no login and no management-interface access required. Affected release trains span BIG-IP 17.1.0, 17.5.0 and 21.1.0, each with its own hotfix, and CISA has set September 25 — tomorrow — as the federal remediation deadline under Binding Operational Directive 26-04. Why it matters: this is the third network-appliance RCE to land in KEV within about a week (Zyxel GS1900, MikroTik RouterOS, now F5 APM), and the shared failure mode — memory corruption reachable through an unauthenticated protocol handler that's supposed to be enforcing access control — is exactly the bug class a fuzzer finds in a hand-rolled OAuth or TLS parser on an ESP32-S3 or STM32 project just as readily as in a data-center load balancer.

<b>1. Post: Security wake-up — the access-control feature that became the way in</b>
A single OAuth setting turned F5's flagship access-control appliance into an unauthenticated open door.

CVE-2026-94127 is a heap-based buffer overflow in BIG-IP APM's OAuth handling, CVSS 9.8. Any virtual server combining an APM access policy with an OAuth profile can be hit with crafted network traffic that corrupts heap memory and executes arbitrary code — before authentication, from the data plane, no management-interface access needed. F5 patched it September 22; CISA added it to its Known Exploited Vulnerabilities catalog the same day and gave federal agencies until September 25 to remediate.

The detail that stands out: this bug lives in the exact code path meant to enforce access control. The feature protecting the network became the entry point into it — the same lesson embedded engineers relearn whenever a bounds check gets skipped in a protocol parser.

<b>2. Post: Integration leap — an RTOS that now ships its own OTA pipeline</b>
Canonical just built a 15-year support promise and a full OTA pipeline into an RTOS that historically gave you neither.

Zephyr 26.04 LTS, announced September 21 as part of Ubuntu Pro for Devices, extends upstream Zephyr's standard 5-year support window out to 15 years and ships with Golioth's OTA and device-management SDK built in by default, not bolted on later.

That matters because the EU Cyber Resilience Act now requires manufacturers to keep shipping security updates for a product's expected lifetime, which for an industrial MCU device can run a decade or more. Most teams solve that by hand-rolling a firmware-update client on top of MCUboot and hoping the credential provisioning holds up. Having a maintained OTA and provisioning pipeline as a first-class part of the RTOS distribution — not a separate integration project — changes whether you build that tooling in-house at all.

<b>3. Post: Regulatory shift — "give users their own data" just became a design law</b>
Since September 12, letting users pull their own data out of a device stopped being a nice-to-have and became a legal design requirement in the EU.

The EU Data Act's Article 3(1) "access by design and by default" obligation now applies to every connected product placed on the EU market. Users must be able to access the data their own device generates directly — easily, securely, free of charge, in a structured, machine-readable format — without needing the manufacturer to hand it over on request.

The obligation only applies "where relevant and technically feasible," but that carve-out does less work than it sounds: if your product has a companion app or cloud backend, technical feasibility is hard to argue against. For anyone designing a connected IoT product for the EU market, this is now an architecture decision made at spec time, not a data-export feature bolted on before a compliance audit.

Is your current project's data model built for the user to pull their own history out, or only for your backend to read it?

<b>4. Post: Physics-meets-architecture — 1 milliwatt of standby on a quad-core Linux part</b>
1 milliwatt in standby, and fast enough back to full operation that the network connection never notices it left.

Renesas' new RZ/G3L and RZ/G3SE MPUs pack up to four Cortex-A55 cores at 1.2 GHz plus a 200 MHz Cortex-M33 real-time coprocessor, and hit around 1 mW standby with quick resume from deep sleep — a number usually associated with MCU-class parts, not quad-core application processors running Linux-class workloads.

The architectural trick is the split: the always-on M33 coprocessor keeps housekeeping and wake logic running at MCU-level power while the whole A55 cluster stays fully powered down, only spinning up for actual application work — HMI rendering on the RZ/G3L, basic display and IoT-gateway duty on the RZ/G3SE. Same heterogeneous-core pattern showing up across the industry, here pushed to genuinely low standby numbers on an applications processor.

<b>5. Post: Tooling unlock — Arm just open-sourced the last closed pieces of its own compiler</b>
Arm just admitted the parts of its own compiler that weren't already open source were the parts holding it back.

Arm's next-generation Toolchain for Embedded is retiring the proprietary linker, C library and binutils it inherited from Arm Compiler 6, replacing them with the LLVM linker and Picolibc — making it the first fully open-source compilation toolchain Arm has shipped for Cortex-M and Cortex-A embedded targets. A safety-qualified variant for functional-safety projects is expected by the end of 2026.

The practical upside isn't philosophical. A fully open toolchain means the linker behavior, libc internals and startup code you're debugging at 2am are all readable and patchable instead of living behind a proprietary black box — the same reason GCC-based toolchains stayed popular even when Arm's own compiler often generated tighter code.

Worth trying on a side project before it becomes the default your vendor SDK quietly switches you to.
